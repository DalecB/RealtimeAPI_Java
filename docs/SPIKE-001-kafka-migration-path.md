# SPIKE-001: Kafka 도입 설계 검증

**상태:** Phase 2 완료 — 단일 릴레이·토픽·트림·PostgreSQL 적재 컨슈머·Testcontainers 왕복·컨슈머 재시작·2인스턴스 재할당 검증 완료 (2026-07-27 작성, 2026-08-12 완료) / Phase 3 릴레이 자동 인계 1차 구현·단건 검증 완료, 나머지 실패 정책 미구현 (2026-08-18)
**관련 결정:** [PRD ADR-009](PRD.md) — Audit Log 소비 도입 여부와 전송 계층 선택

## 이 문서가 있는 이유

ADR-009가 Kafka 채택을 확정했다. 이 문서는 **그 결정을 실무에서 쓰이는 스펙으로 구현하기 위해 무엇에 답해야 하는지**를 고정한다.

Kafka는 "붙이면 도는" 종류가 아니다. 브로커를 띄우고 토픽 하나에 컨슈머 하나를 붙이면 동작은 하지만, 그 상태는 운영 스펙이 아니다. 아래 검증 항목은 **동작 확인이 아니라 결정과 근거**를 산출물로 한다. 구성이 뜨는 것은 검증의 시작점이지 결과가 아니다.

### Phase 2 완료 범위

- Redis Streams를 아웃박스로 사용하고 단일 릴레이가 Kafka로 전달한다.
- 릴레이는 고정 컨슈머 이름을 사용하며, 재시작 시 자신이 읽었지만 XACK하지 못한 메시지를 다시 처리한다.
- Kafka 컨슈머는 원본 감사 이벤트를 PostgreSQL에 저장하고 `(leaderboard_id, event_id)` 고유 제약으로 중복 저장을 막는다.
- Testcontainers로 Lua XADD → 릴레이 → Kafka → PostgreSQL 왕복, 중복 전달, 컨슈머 재시작을 검증했다.
- 실제 애플리케이션 2개로 Kafka 컨슈머 파티션 재할당을 검증했다. 릴레이는 한 인스턴스에서만 실행했다.
- Redis 릴레이 미수신·미확인 건수와 Kafka 컨슈머 지연을 내부 API와 운영 화면에서 확인할 수 있다.

공식 Redis 256MB 환경의 5분 E2E에서 `990.44 RPS`, HTTP p99 `3.99ms`, 오류율 `0%`를 확인했다. Kafka와 PostgreSQL은 각각 `300,001건`을 처리했고 Redis 미수신·미확인 및 Kafka 미처리 메시지는 모두 `0건`으로 해소됐다.

## 선결 쟁점: ADR-002와의 충돌 〔B 채택 — 2026-07-29〕

ADR-002는 XADD를 Lua 블록 안에 넣어 "점수는 반영됐는데 감사 로그에 누락"되는 상황을 원천 차단했다. **Kafka 프로듀서는 Lua 블록 안에 들어갈 수 없다.** 따라서 원자성 보장을 어디로 옮길지가 Kafka 도입의 선결 조건이다.

### 검토한 안

| 안                                     | 구조                                                       |
| -------------------------------------- | ---------------------------------------------------------- |
| **A. Redis 성공 후 Kafka 발행**        | 핫패스에서 Lua 성공 → 그 자리에서 Kafka에 발행             |
| **B. Redis Streams를 아웃박스로 사용** | Lua의 XADD 유지 → 별도 릴레이가 스트림을 읽어 Kafka로 전달 |
| **C. XADD를 Kafka로 대체**             | Lua에서 XADD 제거, 기록은 Kafka에만                        |

### 판별 기준

갈림길은 하나다 — **원자 블록 안에 내구적 기록이 남는가.**

서로 다른 두 시스템에 걸친 쓰기에는 원자적 커밋이 없다. 분산 트랜잭션은 비용과 가용성 때문에 선택지가 아니다. 그러므로 남는 방법은 **한 시스템 안에서 원자적으로 쓰고, 그 기록을 비동기로 옮기는 것**뿐이다. 기록이 내구적이면 옮기는 쪽은 안전하게 재시도할 수 있다.

### 결정: B

Lua의 4연산 원자성을 유지하되, 스트림의 역할을 **최종 저장소에서 아웃박스로** 바꾼다. 릴레이가 스트림을 읽어 Kafka로 옮기고, Kafka는 내구성 있는 중간 저장소이자 소비 계층이 된다. 최종 감사 로그는 컨슈머가 PostgreSQL에 저장한다. ADR-002는 뒤집히지 않고 유지된다.

### 탈락 사유

**C — 유실을 감지할 수도 복원할 수도 없다.** Lua가 끝난 뒤 Kafka에 발행하기 전에 프로세스가 죽으면 그 기록은 영구 유실된다. 복구 시 대조하려 해도 비교 대상이 없다.

- ZSET은 **집계**다. score가 500일 때 100×5인지 100×4에 1건 누락인지 구분할 수단이 없다. 로그 한 건이 빠져도 집계에는 흔적이 남지 않는다.
- 멱등키는 `v2:<payloadHash>:<processedAt>` 형식으로 **해시**를 담는다. "이 키로 무언가 처리됐다"는 알 수 있어도 userId·delta를 복원할 수 없다. TTL 24시간이 지나면 그 흔적조차 없다.

즉 C의 비용은 "복구가 비싸다"가 아니라 **"유실을 알 방법이 없다"** 이다.

**A — 독립된 안이 아니다.** A는 Kafka 발행 실패를 어떻게 다루느냐에 따라 둘로 나뉜다.

- 실패를 처리한다면 스트림에서 재전송해야 하고, 그것이 곧 **B**다.
- 처리하지 않는다면 기록이 유실되고, 그것이 곧 **C**다.

중간 상태로 유지되지 않으므로 별도 안으로 세우지 않는다.

### B의 비용

릴레이 구간에는 **최소 한 번 전달(at-least-once) 방식에서 생기는 중복 가능 구간**이 있다. `XREADGROUP` → Kafka 발행 → `XACK` 순서에서 발행 성공 후 XACK 전에 프로세스가 종료되면, 같은 컨슈머 이름으로 재시작한 릴레이가 즉시 재발행하거나 다른 이름의 교체 릴레이가 `min-idle-time` 이후 인계해 재발행한다. 중복은 컨슈머의 멱등 처리로 흡수한다. 교체 인계는 단건 happy-path만 검증했고 종료 주입과 나머지 경계 검증은 없으므로, 전체 릴레이 경로가 최소 한 번 전달을 보장한다고 확대 해석하지 않는다.

## 확정된 구현 결정 (2026-07-29)

### 릴레이 위치 — 애플리케이션 내부

`@Scheduled` 기반으로 앱 안에 둔다. ADR-003의 스냅샷 워커와 같은 형태이며, 배포 단위를 하나로 유지한다.

비용: 핫패스와 JVM 힙·커넥션을 공유한다. 릴레이 처리가 밀리면 API 응답에도 영향을 줄 수 있으므로, 처리량이 문제가 되면 별도 프로세스로 분리한다.

### 파티션 키 — `leaderboardId`

**근거**: 추이 집계는 리더보드 단위로 이루어진다. 이상 탐지도 대개 한 리더보드 안에서의 유저 행동을 보므로, 이 키로도 해당 유저의 이벤트가 한 파티션에 순서대로 모인다.

**비용**: PRD `0. Scenario`가 선언한 리더보드 단위 트래픽 편향이 그대로 파티션 편중이 된다. 한 키는 여러 파티션으로 나눌 수 없으므로 뜨거운 리더보드는 컨슈머를 늘려도 병렬 처리되지 않는다. 또한 리더보드 개수가 유효 병렬도의 상한이 된다.

**받아들이는 이유**: 시스템 전체 피크가 1,000/s이므로 파티션 하나가 전부 받아도 Kafka 처리 범위 안이다.

**상한에 닿았을 때의 경로**: 복합 키(`leaderboardId:bucket`)로 뜨거운 리더보드만 여러 파티션에 분산한다. 대가는 리더보드 단위 순서 보장을 잃는 것이다. 현 규모에서는 필요하지 않으므로 도입하지 않는다.

### 순서 보장 범위

리더보드 단위로 보장된다. 서로 다른 리더보드 사이에는 순서가 없다. 컨슈머는 이를 전제로 작성한다.

### replay — 기록하지 않음

멱등키가 존재하는 재요청은 정상적인 클라이언트 재시도이며 이상 탐지 신호로서 값이 낮다. 건수는 `idempotency_hit_total`로 이미 계측되고 있으므로 추세 파악은 가능하다.

현재 Lua는 멱등키가 존재하면 XADD 전에 early return 하므로 **이 동작은 기존 코드 그대로다**(`process_event.lua:10-16`, `ProcessEventConcurrencyTest`가 동시 50건에 `XLEN = 1`을 단언).

### 409 (멱등키 재사용 충돌) — Lua에서 기록

동일 키에 다른 payload가 오는 경우는 클라이언트의 키 생성 버그이거나 변조 시도이므로 이상 탐지에서 값이 높다. 따라서 감사 기록에 남긴다.

Lua가 저장된 값과 들어온 값의 해시 부분을 비교해 불일치일 때 XADD 한다. 원자성 때문이 아니다 — 409는 점수가 반영되지 않은 경로라 ADR-002가 막으려는 상황 자체가 없다. **스트림에 쓰는 곳을 한 군데로 유지하기 위해서다.** 생산자가 둘이 되면 필드 구성과 실패 처리를 두 군데서 맞춰야 한다.

PRD `7.2 Lua 제약 조건`의 반복문 금지를 지키기 위해, 구분자 위치는 `string.find`로 찾고 `string.sub`으로 자른다. 순회하지 않는다.

### 아웃박스 트림 — 그룹의 미처리 워터마크까지만

별도 워커(`AuditStreamTrimWorker`)가 40초 주기로 돌며 `XTRIM key MINID <워터마크>`를 실행한다.

**고정 길이나 고정 기간으로 자르지 않는다.** `MAXLEN`은 읽혔는지를 보지 않으므로, 릴레이 처리가 밀린 상태에서 트림이 앞지르면 **아직 Kafka로 옮기지 못한 엔트리가 오류 없이 삭제된다.** 유실 방지를 위한 아웃박스가 오히려 감지되지 않는 유실을 만드는 상태다.

**워터마크 원칙 — 확신할 수 있을 때만 자르고, 확신 없으면 안 자른다.** 트림은 지우기만 하므로 중복은 못 만들지만, 아직 못 옮긴 것을 지우면 유실이다. 그래서 워터마크는 옮김이 끝난 지점을 넘지 않는다.

| 상태               | 워터마크                             | 근거                                                                                   |
| ------------------ | ------------------------------------ | -------------------------------------------------------------------------------------- |
| 미확인 메시지 있음 | `XPENDING`의 가장 오래된 메시지 ID   | 그 뒤는 아직 XACK 안 됐다. 앞까지만 안전                                               |
| 미처리 없음        | `XINFO GROUPS`의 `last-delivered-id` | 배달된 게 전부 XACK됐다는 뜻이므로 받아간 지점까지 전부 안전                           |
| 그룹 없음          | 없음(건너뜀)                         | 아무것도 안 옮겨졌다. 자를 근거가 없다. 릴레이가 그룹을 만들면 다음 주기부터 정상 작동 |

워터마크는 현재 단일 릴레이에서도 **그룹 전체** 기준으로 계산한다. 이 기준은 향후 릴레이가 여러 개가 되어도 한 인스턴스의 진행 지점만 보고 다른 인스턴스가 처리 중인 엔트리를 지우지 않게 한다. 단, 트림의 다중 인스턴스 안전성과 중단된 릴레이가 남긴 미처리 메시지 인계는 별개다. 후자는 Phase 2에서 지원하지 않는다.

기존 `MAXLEN ~ 100000`은 그대로 둔다. 릴레이가 영구히 멈췄을 때 무한 증식을 막는 최후 방어선이다.

### 릴레이 구성값

| 값          | 설정                         | 비고                                                                                                                                                                                                                                                                         |
| ----------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 릴레이 주기 | 5초                          | 한 주기 안에서 **스트림이 빌 때까지 반복해서** 읽는다. 한 번에 가져오는 건수를 고정하면 유입이 그보다 많을 때 밀린 양이 줄지 않는다 (피크 1,000/s면 5초에 5,000건)                                                                                                           |
| 트림 주기   | 40초                         | 이미 옮긴 엔트리를 정리하는 주기. 유실 위험이 아니라 메모리를 줄이는 값이다 — `MAXLEN`은 오래된 것부터 지우므로 이미 옮긴 것이 먼저 지워진다                                                                                                                                 |
| 컨슈머 이름 | `HOSTNAME`                   | 현재 운용 범위는 단일 릴레이이며 `docker-compose.yml`에서 `hostname`을 고정한다. 같은 이름으로 재시작하면 자기 PEL을 즉시 재처리한다. 다른 이름의 교체 릴레이는 10분 이상 idle인 PEL을 `XAUTOCLAIM`으로 인계하지만, 실제 배포 교체와 10분 유휴 조건은 아직 검증하지 않았다 |
| 스트림 순회 | 리더보드별 반복              | `XREADGROUP`에 여러 스트림을 한 번에 넘기면 왕복이 줄지만, Redis Cluster에서 키가 다른 슬롯이면 `CROSSSLOT`으로 실패한다. `{leaderboardId}` 해시 태그를 붙인 이유(ADR-002)가 Cluster 대비이므로 그 준비를 무효화하지 않는다. `SnapshotCaptureWorker`가 이미 같은 순회 형태다 |
| 그룹 생성   | 매 틱 시도, `BUSYGROUP` 무시 | 새 리더보드의 스트림에는 그룹이 없다. 여러 인스턴스가 동시에 만들어도 하나만 성공하므로 별도 잠금이 필요 없다                                                                                                                                                                |

### 토픽 설정

토픽은 애플리케이션 기동 시 `NewTopic` 빈으로 만든다(`AuditTopicConfig`). 브로커의 auto-create를 껐으므로 이 빈이 없으면 토픽이 없다. 리텐션·정리 정책을 코드로 박아두는 것이 목적이다.

| 값                | 설정              | 비고                                                                                                                                                                                                                                                                                                                           |
| ----------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 이름              | `lb-audit-events` | 하이픈 표기. 점 표기는 계층이 있을 때 쓰는데 이 토픽은 하나뿐이고, Kafka 메트릭에서 `.`과 `_`가 서로 뭉개지는 문제가 있어 피한다                                                                                                                                                                                               |
| 파티션            | 3                 | **처리량이 아니라 Kafka 컨슈머 그룹에서 병렬로 처리할 수 있는 인스턴스 수의 상한이다.** 피크 1,000/s는 파티션 하나로도 남으므로 처리량은 기준이 못 된다. 향후 Kafka 컨슈머 3대까지 부하를 나눠 가질 수 있다는 뜻이며, Redis 릴레이의 다중 인스턴스 지원을 의미하지 않는다. 크게 잡으면 리더보드가 적을 때 빈 파티션만 늘어난다 |
| `retention.ms`    | 30일              | ADR-009 가정 1                                                                                                                                                                                                                                                                                                                 |
| `retention.bytes` | 파티션당 1GB      | **로컬 기준값이다.** 전체 30일 추정치 약 2GB가 세 파티션에 고르게 분산되면 시간 제한이 먼저 적용되지만, 특정 파티션에 1GB를 초과해 몰리면 그 파티션은 용량 제한이 먼저 적용된다                                                                                                                                                |
| `cleanup.policy`  | `delete`          | `compact`는 키마다 마지막 값만 남겨 감사 로그를 파괴한다                                                                                                                                                                                                                                                                       |

**파티션 증설은 별도 검증 항목이다.** 파티션 수가 바뀌면 `hash(key) % partitionCount` 결과도 달라져 같은 `leaderboardId`의 새 메시지가 다른 파티션으로 이동할 수 있다. 기존 파티션과 새 파티션을 동시에 소비하는 동안에는 리더보드 단위 순서를 보장할 수 없다. 컨슈머 지연이 계속 증가하거나 특정 파티션에 트래픽이 몰릴 때 증설을 검토하되, 실행 전 다음을 결정한다.

- 기존 메시지를 모두 처리한 뒤 파티션을 늘릴지
- 새 토픽을 만들고 프로듀서·컨슈머를 순서대로 전환할지
- 증설 전후 리더보드 단위 순서가 필요한 컨슈머를 어떻게 중지·재개할지

**호스트와 compose 양쪽에서 접속하려면 리스너가 둘이어야 한다**: 브로커는 클라이언트가 처음 붙은 뒤 "이 주소로 다시 연결하라"고 접속 주소를 돌려준다. 이 주소를 `kafka:9092` 하나로만 두면 compose 네트워크 밖(호스트의 `bootRun`·테스트)에서는 그 이름을 못 찾는다. 그래서 안쪽용(`INTERNAL://kafka:9092`)과 바깥쪽용(`EXTERNAL://localhost:29092`)을 나눠 둔다.

### 트림 기준 — 그룹 전체의 미처리 최솟값

D-010에서는 "릴레이가 마지막으로 Kafka에 발행한 엔트리 ID"를 기준으로 잘랐으나, 이 방식은 릴레이 인스턴스가 여러 개일 때 **안전하지 않다.** 컨슈머 그룹이 엔트리를 나눠 주므로 한 인스턴스의 진행 지점 앞에 다른 인스턴스가 아직 처리 중인 엔트리가 있을 수 있다.

기준은 `XPENDING`이 돌려주는 **그룹 전체에서 가장 오래된 미처리 ID**다. 그 앞은 모든 인스턴스가 끝낸 구간이므로 자를 수 있다. 미처리가 하나도 없으면 그룹이 마지막으로 받아간 지점까지 자른다.

### 릴레이 처리 순서 — Kafka 발행 먼저, XACK 나중, 미확인 메시지 먼저

한 스트림을 처리하는 순서다(`AuditRelayWorker`).

1. **현재 릴레이의 미확인 메시지 재처리** — `XREADGROUP ... 0`으로 이 컨슈머가 **읽었지만 아직 XACK하지 못한 항목**을 다시 읽는다. 같은 `consumerName`의 릴레이가 계속 실행되거나 같은 이름으로 재시작하면 한 주기 안에 다시 처리한다.
2. **다른 릴레이의 오래된 PEL 인계** — 복구 배치 한도가 남으면 `XAUTOCLAIM`으로 `min-idle-time`을 넘긴 항목을 현재 컨슈머로 옮긴다.
3. **새 기록 처리** — `XREADGROUP ... >`이 빈 결과를 반환할 때까지 반복한다.
4. 각 배치: **모두 Kafka에 발행 → 성공을 확인한 항목만 XACK.** 실패한 항목은 미확인 상태로 남겨 다음 주기에 재시도한다.

**Kafka 발행 성공을 확인하기 전에 XACK하면 안 된다.** XACK 직후 Kafka 발행 전에 프로세스가 종료되면 Redis의 미확인 목록과 Kafka 양쪽에 기록이 남지 않아 유실된다. "Kafka 발행은 성공했지만 XACK 전에 종료"되면 같은 `consumerName`으로 재시작한 릴레이가 즉시 재발행하거나, 다른 이름의 교체 릴레이가 `min-idle-time` 이후 인계해 재발행한다. 컨슈머는 중복을 멱등하게 처리한다. 단, 이 종료 시점의 failure injection은 아직 수행하지 않았다.

### 현재 운용 경계와 Phase 3 정책

**Phase 2 완료 당시에는 단일 릴레이 + 고정 컨슈머 이름으로 제한했다.** `docker-compose.yml`의 `hostname: realtime-api`를 유지하고, 재시작한 릴레이가 `XREADGROUP ... 0`으로 자신의 PEL을 재처리했다. Phase 3 1차 구현은 다른 이름의 교체 릴레이가 오래된 PEL을 인계하는 코드 경로를 추가했지만, 정상 상태의 동시 다중 릴레이 구성은 여전히 보장하지 않는다.

#### Phase 3 범위

Phase 3는 **다른 이름의 단일 릴레이로 교체되는 상황**을 지원한다. 정상 상태에서 여러 릴레이를 동시에 실행하는 구성은 범위 밖이다.

- 컨슈머 이름은 인스턴스가 실행되는 동안 유지하고, 교체된 인스턴스마다 다르게 부여한다.
- 이전 릴레이가 남긴 PEL은 새 릴레이가 `XAUTOCLAIM`으로 인계한다.
- 전달 방식은 최소 한 번 전달이다. 중복 발행은 허용하고 `(leaderboard_id, event_id)` 고유 제약으로 중복 저장을 막는다.
- 새 릴레이도 XACK 전에 종료되면 다음 릴레이가 같은 방식으로 다시 인계한다.

#### 릴레이 인계 정책

| 항목            | 결정                        | 근거                                                                                                                                                                |
| --------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `min-idle-time` | 10분                        | Kafka 프로듀서 기본 `delivery.timeout.ms` 120초보다 길게 두어 정상 처리 중인 메시지를 인계할 가능성을 낮춘다. 임시값이며 릴레이 배치 처리시간을 측정한 뒤 조정한다. |
| 복구 우선순위   | 복구 배치 후 새 메시지 처리 | 오래된 미처리 메시지를 먼저 처리하되 새 메시지 지연을 제한한다.                                                                                                     |
| 복구 배치 한도  | 스트림별 주기당 총 500건    | 현재 릴레이 배치 크기를 사용한다. 현재 컨슈머의 PEL 재처리와 다른 컨슈머의 PEL 인계를 합쳐 500건을 넘기지 않는다.                                                   |
| 남은 PEL        | 다음 주기에 이어서 처리     | `XAUTOCLAIM`이 반환한 커서부터 다음 복구 배치를 조회한다. 커서가 `0-0`이면 처음부터 다시 조회한다.                                                                  |
| 발행·확인 순서  | Kafka 발행 성공 후 XACK     | XACK 후 Kafka 발행 전에 종료되어 발생하는 유실을 막는다.                                                                                                            |

한 스트림의 처리 순서는 다음과 같다.

1. 현재 컨슈머의 PEL을 먼저 조회한다.
2. 복구 배치 한도가 남으면 다른 컨슈머의 PEL을 `XAUTOCLAIM`으로 인계한다.
3. 복구 배치를 Kafka에 발행하고 성공한 메시지만 XACK한다.
4. 새 메시지를 처리한다.
5. 남은 PEL은 다음 릴레이 주기에 이어서 처리한다.

다른 컨슈머의 PEL을 인계할 때만 `min-idle-time`을 적용한다. 새 릴레이가 인계한 뒤 발행에 실패한 메시지는 새 릴레이의 PEL에 남기고 다음 주기에 다시 처리한다.

#### 릴레이 자동 인계 1차 구현·검증 (2026-08-18)

`AuditRelayWorker`에 현재 컨슈머의 PEL 재처리 → `XAUTOCLAIM`으로 다른 컨슈머의 오래된 PEL 인계 → 새 메시지 처리 순서를 구현했다. `XAUTOCLAIM`의 반환 커서는 리더보드별로 보관하며, Kafka 발행에 성공한 엔트리만 XACK하는 기존 규칙을 그대로 사용한다.

Testcontainers 통합 테스트 `stalePendingMessage_isClaimedByReplacementRelay_andStoredOnce`는 릴레이 A 역할의 임시 컨슈머가 `XREADGROUP` 후 XACK하지 않아 PEL을 남기고, 교체 릴레이가 이를 인계해 PostgreSQL에 1행만 저장하며 PEL을 0으로 만드는 흐름을 검증한다. 테스트에서는 대기 시간을 없애기 위해 `claim-min-idle-ms=0`을 사용했다. 전체 `./gradlew test`도 통과했다.

아직 검증하지 않은 경계는 실제 10분 유휴 조건, 500건 초과 시 반환 커서 연속 처리, Kafka 발행 성공 후 XACK 전 종료 주입, 인계받은 릴레이의 재종료다. `docker-compose.yml`은 고정 hostname을 유지하므로 실제 배포에서 서로 다른 컨슈머 이름으로 교체되는 구성도 별도 검증이 필요하다.

#### Kafka 컨슈머 실패 처리

파싱·레코드 검증 실패와 PostgreSQL 일시 장애를 분리한다.

| 실패                  | 처리                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 파싱·레코드 검증 실패 | 3초 간격으로 최초 시도 포함 총 3회 처리한다. 최종 실패한 레코드만 DLQ(Dead Letter Queue)로 보낸다. DLQ 발행 성공 후 원본 오프셋을 커밋한다. |
| PostgreSQL 일시 장애  | 컨슈머 컨테이너를 일시 중지하고 무기한 재시도한다. 일시 중지 중에도 poll을 계속해 컨슈머 그룹 할당을 유지한다.                              |

PostgreSQL 재시도는 10초부터 시작해 간격을 2배씩 늘리고, 최대 5분으로 제한한다.

```text
10초 → 20초 → 40초 → 80초 → 160초 → 300초 → 이후 300초
```

DB 장애 중에도 릴레이는 Redis Stream의 메시지를 Kafka로 계속 전달한다. Redis 적체 대신 Kafka 컨슈머 지연이 증가하고, DB가 복구되면 같은 배치부터 처리를 재개한다.

#### Phase 3 검증 기준

- 릴레이 A가 Kafka 발행 전에 종료되면 릴레이 B가 10분 이후 PEL을 인계한다.
- 릴레이 A가 Kafka 발행 후 XACK 전에 종료되면 중복 발행이 발생해도 PostgreSQL에는 1행만 남는다.
- 릴레이 B도 XACK 전에 종료되면 다음 릴레이가 다시 인계한다.
- PEL이 500건을 넘으면 다음 릴레이 주기에서 이전 커서부터 처리한다.
- 파싱 실패 레코드는 3초 간격으로 총 3회 실패한 뒤 해당 레코드만 DLQ에 저장한다.
- DLQ 발행에 실패하면 원본 오프셋을 커밋하지 않는다.
- PostgreSQL 장애 중 컨슈머 그룹 할당을 유지하고 Kafka 컨슈머 지연이 증가한다.
- PostgreSQL 복구 후 같은 배치부터 재처리하고 컨슈머 지연이 0으로 돌아온다.

#### 남은 리스크

- 릴레이 배치 처리시간을 측정하지 않았다. 측정 결과에 따라 `min-idle-time` 10분을 조정한다.
- 새 메시지 유입량이 릴레이 처리량을 계속 넘으면 다음 복구 주기가 지연될 수 있다.
- Kafka 컨슈머를 여러 개 실행하면 DB 재시도 시점이 겹칠 수 있다. 지연 시간 분산 여부는 구현 전에 결정한다.
- SQL 오류와 스키마 불일치처럼 DB 복구로 해결되지 않는 오류의 중지·알림 정책은 정하지 않았다.

Phase 3를 완료하기 전에는 `릴레이 장애 자동 인계`, `릴레이 전체 경로의 최소 한 번 전달`, `처리 불가 메시지 DLQ 보관`을 검증 완료로 주장하지 않는다.

### Kafka 컨슈머 재시작·다중 인스턴스 검증 (2026-08-11)

검증 목적은 릴레이를 단일 인스턴스로 유지한 채 Kafka 컨슈머만 늘릴 수 있는지 확인하는 것이다.

구성:

- app-1: 릴레이 활성화, Kafka 컨슈머 활성화
- app-2: 릴레이·스냅샷 워커·콜드 스타트 복구 비활성화, Kafka 컨슈머 활성화
- 두 컨슈머 모두 `audit-trend` 그룹 사용
- 토픽 파티션 3개, `leaderboardId`를 키로 사용

결과:

| 단계            | 파티션 할당                                               | 메시지 처리                                                                                      |
| --------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| app-1만 실행    | app-1 = `0, 1, 2`                                         | 모든 파티션의 컨슈머 지연 0                                                                      |
| app-2 추가      | app-1 = `0, 1`, app-2 = `2`                               | app-2가 파티션 2의 오프셋 `3173`을 처리해 다음 오프셋이 `3174`로 증가했고, PostgreSQL에 1행 저장 |
| app-2 강제 종료 | 기본 `session.timeout.ms=45000` 경과 후 app-1 = `0, 1, 2` | app-1이 파티션 2의 다음 오프셋 `3174 → 3175`를 처리하고 모든 파티션의 컨슈머 지연이 0으로 복귀   |

전체 `audit_events` 행 수는 검증 전 1,889행에서 신규 이벤트 9건 처리 후 1,898행으로 증가했다. 강제 종료 전후 파티션 2에 넣은 두 이벤트는 서로 다른 `eventId`로 각각 1행 저장됐다.

별도 Testcontainers 테스트에서는 리스너를 중지한 동안 같은 파티션에 메시지를 넣고 재시작했다. 첫 메시지의 커밋된 오프셋 이후부터 소비를 재개하고 두 메시지가 각각 1행인지 확인했다. 이 테스트는 리스너 재시작을 다루며 JVM 강제 종료를 재현하지는 않는다.

검증하지 않은 범위:

- DB 저장 성공 후 오프셋 커밋 직전 프로세스 종료
- 강제 종료 과정에서 실제 중복 전달 발생 여부. 중복 저장 방지는 동일 메시지를 두 번 전달하는 별도 테스트로 검증했다.
- API 요청의 인스턴스별 분산
- 단일 릴레이의 1,000 TPS 처리량과 API 응답 시간에 미치는 영향
- 중단된 릴레이가 남긴 미처리 메시지를 다른 릴레이가 인계받는 기능

> **Redis 자체가 죽으면?** 스트림 본문과 컨슈머 그룹의 미확인 메시지 정보는 일반 Redis 데이터이고, `XREADGROUP`/`XACK`은 쓰기 명령이라 AOF에 기록된다. 따라서 재부팅 시 둘이 함께 복구된다(`appendfsync everysec` 기준 최대 1초 유실). Redis Streams 아웃박스는 릴레이 프로세스 중단에 대응하고, AOF/RDB는 Redis 장애에 대응한다. 1초 유실 구간에서 감사 기록이 사라지면 같은 Lua 블록의 점수도 함께 사라지므로 두 데이터가 어긋나지는 않는다(PRD 9 계층별 RPO).

### 릴레이 상태 확인 — 미수신 건수와 미확인 건수

릴레이가 멈추면 Kafka로 아무것도 들어오지 않으므로 **Kafka 컨슈머 지연(lag)은 증가하지 않는다.** Kafka 지표만 보면 릴레이 장애를 확인하기 어렵다.

Redis Stream에서 아직 읽지 않은 항목은 `XINFO GROUPS`의 `lag`, 읽었지만 XACK하지 않은 항목은 `XPENDING`으로 확인한다. 릴레이가 읽기 전에 멈추면 XPENDING 건수는 늘지 않으므로 두 값을 함께 봐야 한다.

현재 `/internal/streams/status`는 릴레이 미수신 건수(`consumerGroupLag`), 미확인 건수(`pendingEntries`), 전체 길이(`streamLength`)를 제공한다. Prometheus에는 `stream_consumer_group_lag`와 `stream_pending_entries`가 등록되어 있다. Kafka 컨슈머 지연은 `/internal/kafka/audit-topic/status`와 Ops Console에서 확인한다. `streamLength`에는 이미 처리했지만 아직 트림하지 않은 항목도 포함되므로 적체량으로 사용하지 않는다.

### 감사 기록 스키마

**필드**

| 필드             | 출처             | 비고                                           |
| ---------------- | ---------------- | ---------------------------------------------- |
| `type`           | Lua 분기         | `new` / `conflict`                             |
| `userId`         | ARGV             |                                                |
| `delta`          | ARGV             | `conflict`일 때는 **거부된(들어온) 값**        |
| `apiKeyId`       | ARGV (신규 추가) | 이상 탐지에서 클라이언트 단위 축               |
| `idempotencyKey` | ARGV (신규 추가) | `conflict` 기록을 원본 요청과 잇는 유일한 수단 |

`leaderboardId`는 값에 넣지 않는다. Kafka 메시지 키로 쓰이며 레코드에 함께 저장되므로 컨슈머가 `record.key()`로 읽는다. 레코드가 다른 토픽이나 시스템으로 복사될 일이 생기면 그때 값에도 추가한다 — 나중에 필드를 늘려도 컨슈머는 깨지지 않는다.

**이벤트 발생 시각**은 별도 필드를 두지 않는다. 스트림 엔트리 ID의 앞부분이 XADD 시점의 밀리초이며, 컨슈머가 이 값을 PostgreSQL의 `event_time`으로 저장한다. 현재 릴레이는 `ProducerRecord`에 타임스탬프를 지정하지 않으므로 Kafka 레코드에는 발행 시각이 들어간다. 따라서 릴레이가 밀린 뒤 오래된 엔트리를 발행해도 적재 직후 `retention.ms` 삭제 대상이 되지는 않는다.

**형식**은 JSON. 스트림의 평평한 필드-값 구조는 Redis의 저장 방식이지 전송 형식이 아니다. 릴레이가 변환 지점이므로 컨슈머가 다루기 쉬운 형식으로 내보낸다. 필드명 반복으로 인한 크기 증가는 `compression.type`으로 흡수한다.

**버전**은 Kafka 헤더에 둔다. 값을 파싱하지 않고도 버전을 알 수 있어 컨슈머가 분기하기 쉽다.

**토픽 정리 정책은 `delete`를 유지한다.** `compact`는 키마다 마지막 값만 남기므로, 리더보드가 키인 이 토픽에 걸면 리더보드당 이벤트 한 건만 남고 나머지가 사라진다. 감사 로그에는 쓸 수 없다.

## 실무 스펙 기준선

데모 수준과 실제 운영 수준을 가르는 최소 조건이다. 지키지 못하는 항목은 **지키지 못했다는 사실과 이유를 문서에 남긴다.**

- **오프셋은 처리 완료 후 커밋한다.** auto-commit을 끄고 `ack-mode=batch`를 사용해 리스너가 정상 반환한 뒤 컨테이너가 배치 오프셋을 커밋한다 (항목 6·11의 전제).
- **컨슈머는 멱등하게 구현한다.** 최소 한 번 전달 방식에서는 중복 처리가 예외가 아니라 정상 경로다. PostgreSQL의 `(leaderboard_id, event_id)` 고유 제약과 `ON CONFLICT DO NOTHING`으로 중복 저장을 막는다.
- **리텐션은 기간과 용량을 병기한다.** 어느 쪽이 먼저 걸리는지를 알고 설정한다.
- **복제 계수는 낮게 가되 근거를 남긴다.** 로컬 compose에서 브로커 3대는 과하다. `replication.factor=1`로 두되 "프로덕션에서는 `acks=all` + `replication.factor≥3` + `min.insync.replicas=2`"를 문서에 명시한다. **아는데 안 한 것과 모르는 것은 구분되어야 한다.**
- **처리 지연은 기존 운영 화면에서 확인한다.** 별도 모니터링 스택을 세우지 않고 내부 API, Prometheus, Ops Console을 사용한다.

## 컨슈머와 저장 (2026-08-07 착수)

첫 컨슈머(`AuditEventConsumer`)가 audit 토픽을 읽어 **원본 이벤트를 PostgreSQL `audit_events`에 적재**한다. ADR-009 가정 2(소비자 복수)를 주장에서 실제로 바꾸는 지점이다.

**원본 적재를 고른 이유**: 추이 집계만 미리 해서 저장하면 작지만, 이상 탐지와 아카이브가 원본을 다시 요구한다. 원본을 두면 downstream이 전부 열린다 — 추이는 이 위의 5분 버킷 집계(`date_bin`), 이상 탐지·아카이브는 원본 그 자체. 데모 규모에선 집계 쿼리가 즉시다. 행 수가 커지면 롤업 요약 테이블이 다음 단계.

**멱등은 DB가 맡는다**: 릴레이의 재전송이나 Kafka 컨슈머의 재처리로 같은 이벤트가 두 번 올 수 있다. `UNIQUE (leaderboard_id, event_id)` + `ON CONFLICT DO NOTHING`으로 중복을 집계 전에 제외한다. 집계가 두 번 반영되면 유저가 이상 탐지 등에서 불이익을 받는다. **엔트리 ID는 한 리더보드 스트림 안에서만 고유**하므로 `leaderboard_id`와 함께 유일성 조건을 구성한다. 릴레이는 메시지에 엔트리 ID(`eventId`)를 포함한다.

**오프셋은 처리 후 커밋**: 배치 리스너 + `auto-commit=false`. 컨테이너가 배치를 적재한 뒤에만 오프셋을 커밋한다(릴레이의 XACK와 같은 규칙). 배치 크기는 `max-poll-records`(개수)와 poll 주기(시간) 중 먼저 걸리는 쪽이다.

### 저장 티어링 — hot(PG) / cold(객체 스토리지)

30일치 원본은 두 가지가 걸린다: PG 인스턴스 안에서 매 집계 쿼리의 스캔 대상이 되는 성능 부담(비용이 아니라 성능 — 3GB 저장 자체는 PG에서 무시할 수준), 그리고 자주 안 꺼내는 데이터를 비싼 저장소에 두는 것.

- **hot** — 최근 원본 + 추이(집계)는 **PG**. 자주 조회, 작다.
- **cold** — **30일 지난 원본은 객체 스토리지로 아카이브.** 하루 단위 파일(`20260812`, `20260813`, …)로 기록한다. 특정 구간만 다운로드해 이상 조사·감사에 쓴다.

객체 스토리지의 진짜 비용은 저장이 아니라 다운로드(egress)이므로 "거의 안 꺼내는 원본"에만 이득이다. 자주 조회하는 추이는 PG에 두는 이 분리가 맞다. (카바 session-revocation 사례는 수백 노드가 같은 데이터를 반복 다운로드하는 **fan-out 배포** 문제라 S3가 답이었지만, 우리 조회 패턴은 그게 아니므로 이유를 그대로 가져오지 않는다.)

로컬 데모에 객체 스토리지를 붙이는 것은 비목표다. 티어링 설계를 문서로 남기는 것이 목적.

### 이상 탐지 (3·5번) — 필드 확장 선행

평균 대비 이상 점수 탐지, payload 변형 요청 목록은 현재 엔트리(`userId`, `delta`)만으로는 한계가 있다 — 출처·디바이스 등 필드 확장이 선행될 가능성이 높다(항목 10 스키마 정책). 원본이 `audit_events`에 이미 쌓이므로 조회 기반은 확보돼 있다.

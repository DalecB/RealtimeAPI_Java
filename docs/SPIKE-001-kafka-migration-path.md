**상태**

## 이 문서가 있는 이유

ADR-009가 Kafka 채택을 확정했다. 이 문서는 **그 결정을 실무에서 쓰이는 스펙으로 구현하기 위해 무엇에 답해야 하는지**를 고정한다.

Kafka는 브로커와 컨슈머를 실행하는 것만으로 운영 요구사항을 충족하지 않는다. 아래 검증 항목은 단순한 동작 확인이 아니라 **결정과 근거**를 산출물로 한다. 구성 요소의 실행 여부는 검증의 시작점이지 결과가 아니다.

### Phase 2 완료 범위

- Redis Streams를 아웃박스로 사용하고 단일 릴레이가 Kafka로 전달한다.
- 릴레이는 고정 컨슈머 이름을 사용하며, 재시작 시 자신이 읽었지만 XACK하지 못한 메시지를 다시 처리한다.
- Kafka 컨슈머는 원본 감사 이벤트를 PostgreSQL에 저장하고 `(leaderboard_id, event_id)` 고유 제약으로 중복 저장을 막는다.
- Testcontainers로 Lua XADD → 릴레이 → Kafka → PostgreSQL 왕복, 중복 전달, 컨슈머 재시작을 검증했다.
- 실제 애플리케이션 2개로 Kafka 컨슈머 파티션 재할당을 검증했다. 릴레이는 한 인스턴스에서만 실행했다.
- Redis 릴레이 미수신·미확인 건수와 Kafka 컨슈머 지연을 내부 API와 운영 화면에서 확인할 수 있다.

공식 Redis 256MB 환경의 5분 E2E에서 `990.44 RPS`, HTTP p99 `3.99ms`, 오류율 `0%`를 확인했다. Kafka와 PostgreSQL은 각각 `300,001건`을 처리했고 Redis 미수신·미확인 및 Kafka 미처리 메시지는 모두 `0건`으로 해소됐다.

## 선결 쟁점: ADR-002와의 충돌 〔B 채택, 2026-07-29〕

ADR-002는 XADD를 Lua 블록 안에 넣어 "점수는 반영됐는데 감사 로그에 누락"되는 상황을 원천 차단했다. **Kafka 프로듀서는 Lua 블록 안에 들어갈 수 없다.** 따라서 원자성 보장을 어디로 옮길지가 Kafka 도입의 선결 조건이다.

### 검토한 안

| 안                                     | 구조                                                       |
| -------------------------------------- | ---------------------------------------------------------- |
| **A. Redis 성공 후 Kafka 발행**        | 핫패스에서 Lua 성공 → 그 자리에서 Kafka에 발행             |
| **B. Redis Streams를 아웃박스로 사용** | Lua의 XADD 유지 → 별도 릴레이가 스트림을 읽어 Kafka로 전달 |
| **C. XADD를 Kafka로 대체**             | Lua에서 XADD 제거, 기록은 Kafka에만                        |

### 판별 기준

판별 기준은 **원자 블록 안에 내구적 기록이 남는가**이다.

서로 다른 두 시스템에 걸친 쓰기에는 원자적 커밋이 없다. 분산 트랜잭션은 비용과 가용성 때문에 선택지가 아니다. 그러므로 남는 방법은 **한 시스템 안에서 원자적으로 쓰고, 그 기록을 비동기로 옮기는 것**뿐이다. 기록이 내구적이면 옮기는 쪽은 안전하게 재시도할 수 있다.

### 결정: B

Lua의 4연산 원자성을 유지하되, 스트림의 역할을 **최종 저장소에서 아웃박스로** 바꾼다. 릴레이가 스트림을 읽어 Kafka로 옮기고, Kafka는 내구성 있는 중간 저장소이자 소비 계층이 된다. 최종 감사 로그는 컨슈머가 PostgreSQL에 저장한다. ADR-002는 뒤집히지 않고 유지된다.

### 탈락 사유

**C: 유실을 감지하거나 복원할 수 없다.** Lua가 끝난 뒤 Kafka에 발행하기 전에 프로세스가 종료되면 그 기록은 영구 유실된다. 복구 시 대조할 데이터도 남지 않는다.

- ZSET은 **집계**다. score가 500일 때 100×5인지 100×4에 1건 누락인지 구분할 수단이 없다. 로그 한 건이 빠져도 집계에는 흔적이 남지 않는다.
- 멱등키는 `v2:<payloadHash>:<processedAt>` 형식으로 **해시**를 담는다. "이 키로 무언가 처리됐다"는 알 수 있어도 userId·delta를 복원할 수 없다. TTL 24시간이 지나면 그 흔적조차 없다.

즉 C의 비용은 "복구가 비싸다"가 아니라 **"유실을 알 방법이 없다"** 이다.

**A는 독립된 대안이 아니다.** Kafka 발행 실패를 처리하는 방법에 따라 다음 두 경우로 나뉜다.

- 실패를 처리한다면 스트림에서 재전송해야 하고, 그것이 곧 **B**다.
- 처리하지 않는다면 기록이 유실되고, 그것이 곧 **C**다.

중간 상태로 유지되지 않으므로 별도 안으로 세우지 않는다.

### B의 비용

릴레이 구간에는 **최소 한 번 전달(at-least-once) 방식에서 생기는 중복 가능 구간**이 있다. `XREADGROUP` → Kafka 발행 → `XACK` 순서에서 발행 성공 후 XACK 전에 프로세스가 종료되면, 같은 컨슈머 이름으로 재시작한 릴레이가 즉시 재발행하거나 다른 이름의 교체 릴레이가 `min-idle-time` 이후 메시지를 인계해 재발행한다. 컨슈머는 이 중복을 멱등하게 처리한다. Testcontainers에서는 반환 커서 기반 후속 배치 처리, Kafka 발행 후 XACK 전 중복과 PostgreSQL 멱등 저장을 검증했다. Compose에서는 Kafka 발행 전 A를 실제 `SIGKILL`하고 운영값 10분 이후 B가 PEL을 인계하는 경로를 검증했다.

## 확정된 구현 결정 (2026-07-29)

### 릴레이 위치: 애플리케이션 내부

`@Scheduled` 기반으로 앱 안에 둔다. ADR-003의 스냅샷 워커와 같은 형태이며, 배포 단위를 하나로 유지한다.

비용: 핫패스와 JVM 힙·커넥션을 공유한다. 릴레이 처리가 밀리면 API 응답에도 영향을 줄 수 있으므로, 처리량이 문제가 되면 별도 프로세스로 분리한다.

### 파티션 키: `leaderboardId`

**근거**: 추이 집계는 리더보드 단위로 이루어진다. 이상 탐지도 대개 한 리더보드 안에서의 유저 행동을 보므로, 이 키로도 해당 유저의 이벤트가 한 파티션에 순서대로 모인다.

**비용**: PRD `0. Scenario`가 선언한 리더보드 단위 트래픽 편향이 그대로 파티션 편중이 된다. 한 키는 여러 파티션으로 나눌 수 없으므로 뜨거운 리더보드는 컨슈머를 늘려도 병렬 처리되지 않는다. 또한 리더보드 개수가 유효 병렬도의 상한이 된다.

**받아들이는 이유**: 시스템 전체 피크가 1,000/s이므로 파티션 하나가 전부 받아도 Kafka 처리 범위 안이다.

**상한에 닿았을 때의 경로**: 복합 키(`leaderboardId:bucket`)로 뜨거운 리더보드만 여러 파티션에 분산한다. 대가는 리더보드 단위 순서 보장을 잃는 것이다. 현 규모에서는 필요하지 않으므로 도입하지 않는다.

### 순서 보장 범위

리더보드 단위로 보장된다. 서로 다른 리더보드 사이에는 순서가 없다. 컨슈머는 이를 전제로 작성한다.

### replay: 기록하지 않음

멱등키가 존재하는 재요청은 정상적인 클라이언트 재시도이며 이상 탐지 신호로서 값이 낮다. 건수는 `idempotency_hit_total`로 이미 계측되고 있으므로 추세 파악은 가능하다.

현재 Lua는 멱등키가 존재하면 XADD 전에 early return 하므로 **이 동작은 기존 코드 그대로다**(`process_event.lua`의 멱등키 조회 분기, `ProcessEventConcurrencyTest`가 동시 50건에 `XLEN = 1`을 단언).

### 409(멱등키 재사용 충돌): Lua에서 기록

동일 키에 다른 payload가 오는 경우는 클라이언트의 키 생성 버그이거나 변조 시도이므로 이상 탐지에서 값이 높다. 따라서 감사 기록에 남긴다.

Lua가 저장된 값과 들어온 값의 해시 부분을 비교해 불일치할 때 XADD를 실행한다. 409 응답 경로에서는 점수가 반영되지 않으므로 이 처리는 원자성을 위한 것이 아니다. **스트림에 쓰는 위치를 한 군데로 유지하기 위한 결정이다.** 생산자가 둘이면 필드 구성과 실패 처리를 두 곳에서 일치시켜야 한다.

PRD `7.2 Lua 제약 조건`의 반복문 금지를 지키기 위해, 구분자 위치는 `string.find`로 찾고 `string.sub`으로 자른다. 순회하지 않는다.

### 아웃박스 트림: 그룹의 미처리 워터마크까지만

별도 워커(`AuditStreamTrimWorker`)가 40초 주기로 돌며 `XTRIM key MINID <워터마크>`를 실행한다.

**고정 길이나 고정 기간으로 자르지 않는다.** `MAXLEN`은 처리 여부를 확인하지 않으므로, 트림 기준이 릴레이의 처리 지점을 넘으면 **아직 Kafka로 전달하지 못한 엔트리가 오류 없이 삭제된다.** 유실 방지를 위한 아웃박스가 오히려 감지되지 않는 유실을 만드는 상태다.

**워터마크 원칙은 처리가 끝났다고 확인한 구간만 자르는 것이다.** 트림은 중복을 만들지는 않지만, 아직 전달하지 않은 항목을 지우면 데이터가 유실된다. 따라서 워터마크는 전달이 끝난 지점을 넘지 않는다.

| 상태               | 워터마크                             | 근거                                                                                   |
| ------------------ | ------------------------------------ | -------------------------------------------------------------------------------------- |
| 미확인 메시지 있음 | `XPENDING`의 가장 오래된 메시지 ID   | 그 뒤는 아직 XACK 안 됐다. 앞까지만 안전                                               |
| 미처리 없음        | `XINFO GROUPS`의 `last-delivered-id` | 배달된 게 전부 XACK됐다는 뜻이므로 받아간 지점까지 전부 안전                           |
| 그룹 없음          | 없음(건너뜀)                         | 아무것도 안 옮겨졌다. 자를 근거가 없다. 릴레이가 그룹을 만들면 다음 주기부터 정상 작동 |

워터마크는 현재 단일 릴레이에서도 **그룹 전체** 기준으로 계산한다. 이 기준은 향후 릴레이가 여러 개가 되어도 한 인스턴스의 진행 지점만 보고 다른 인스턴스가 처리 중인 엔트리를 지우지 않게 한다. 단, 트림의 다중 인스턴스 안전성과 중단된 릴레이가 남긴 미처리 메시지 인계는 별개다. 후자는 Phase 2에서 지원하지 않는다.

`MAXLEN ~`은 릴레이가 오래 멈췄을 때 무한 증식을 막는 최후 방어선으로 남긴다. 값은 `events.audit-stream.max-len=1000000`이고 릴레이 최악 중단 시간에 맞췄다. 교체 릴레이는 `min-idle-time` 10분 뒤에 인계하므로 피크 1,000/s 단일 스트림이면 60만 건이 쌓인다. 여기에 여유를 더해 100만 건(피크 기준 약 16분, 스트림당 약 69MB)으로 잡았다. 이전 값 10만 건은 피크 기준 약 100초라 PostgreSQL·Kafka 단기 장애에서도 미전달 기록이 지워졌다(2026-11-16 변경). 16분을 넘는 중단에서는 여전히 오래된 미전달 기록부터 지워진다. `AuditStreamMaxLenTest`가 상한 아래 무손실과 상한 초과 시 오래된 기록 삭제를 고정한다.

### 릴레이 구성값

| 값          | 설정                         | 비고                                                                                                                                                                                                                                                                         |
| ----------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 릴레이 주기 | 5초                          | 한 주기 안에서 **스트림이 빌 때까지 반복해서** 읽는다. 한 번에 가져오는 건수를 고정하면 유입이 그보다 많을 때 밀린 양이 줄지 않는다 (피크 1,000/s면 5초에 5,000건)                                                                                                           |
| 트림 주기   | 40초                         | 이미 옮긴 엔트리를 정리해 메모리 사용량을 줄이는 주기다. `MAXLEN`은 오래된 항목부터 지우므로 이미 전달한 항목이 먼저 삭제된다.                                                                                                                                                 |
| 컨슈머 이름 | `EVENTS_RELAY_CONSUMER_NAME` → `HOSTNAME` → `relay-local` | 기본 재시작은 같은 이름을 사용하고, 교체 시에는 환경변수로 다른 이름을 명시한다. Compose에서 실제 `SIGKILL` 후 10분 이상 idle인 PEL을 교체 릴레이가 인계하는 흐름을 검증했다 |
| 스트림 순회 | 리더보드별 반복              | `XREADGROUP`에 여러 스트림을 한 번에 넘기면 왕복이 줄지만, Redis Cluster에서 키가 다른 슬롯이면 `CROSSSLOT`으로 실패한다. `{leaderboardId}` 해시 태그를 붙인 이유(ADR-002)가 Cluster 대비이므로 그 준비를 무효화하지 않는다. `SnapshotCaptureWorker`가 이미 같은 순회 형태다 |
| 그룹 생성   | 매 틱 시도, `BUSYGROUP` 무시 | 새 리더보드의 스트림에는 그룹이 없다. 여러 인스턴스가 동시에 만들어도 하나만 성공하므로 별도 잠금이 필요 없다                                                                                                                                                                |

### 토픽 설정

토픽은 애플리케이션 기동 시 `NewTopic` 빈으로 만든다(`AuditTopicConfig`). 브로커의 auto-create를 껐으므로 이 빈이 없으면 토픽이 없다. 리텐션·정리 정책을 코드로 박아두는 것이 목적이다.

| 값                | 설정              | 비고                                                                                                                                                                                                                                                                                                                           |
| ----------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 이름              | `lb-audit-events` | 하이픈 표기. 점 표기는 계층이 있을 때 쓰는데 이 토픽은 하나뿐이고, Kafka 메트릭에서 `.`과 `_`가 서로 뭉개지는 문제가 있어 피한다                                                                                                                                                                                               |
| 파티션            | 3                 | **처리량이 아니라 Kafka 컨슈머 그룹에서 병렬로 처리할 수 있는 인스턴스 수의 상한이다.** 피크 1,000/s는 파티션 하나로도 남으므로 처리량은 기준이 못 된다. 향후 Kafka 컨슈머 3대까지 부하를 나눠 가질 수 있다는 뜻이며, Redis 릴레이의 다중 인스턴스 지원을 의미하지 않는다. 크게 잡으면 리더보드가 적을 때 빈 파티션만 늘어난다 |
| `retention.ms`    | 30일              | ADR-009 가정 1                                                                                                                                                                                                                                                                                                                 |
| `retention.bytes` | 파티션당 1GB      | **로컬 기준값이다.** 전체 30일 추정치 약 2GB가 세 파티션에 고르게 분산되면 시간 제한이 먼저 적용되지만, 특정 파티션에 1GB를 초과해 몰리면 그 파티션은 용량 제한이 먼저 적용된다                                                                                                                                                |
| `cleanup.policy`  | `delete`          | `compact`는 키마다 마지막 값만 남겨 감사 로그를 파괴한다                                                                                                                                                                                                                                                                       |

**파티션 증설은 별도 검증 항목이다.** 파티션 수가 바뀌면 `hash(key) % partitionCount` 결과도 달라져 같은 `leaderboardId`의 새 메시지가 다른 파티션으로 이동할 수 있다. 기존 파티션과 새 파티션을 동시에 소비하는 동안에는 리더보드 단위 순서를 보장할 수 없다. 컨슈머 지연이 계속 증가하거나 특정 파티션에 트래픽이 몰릴 때 증설을 검토하되, 실행 전 다음을 결정한다.

- 기존 메시지를 모두 처리한 뒤 파티션을 늘릴지
- 새 토픽을 만들고 프로듀서·컨슈머를 순서대로 전환할지
- 증설 전후 리더보드 단위 순서가 필요한 컨슈머를 어떻게 중지·재개할지

**호스트와 compose 양쪽에서 접속하려면 리스너가 둘이어야 한다.** 브로커는 클라이언트의 최초 접속 이후 다시 연결할 주소를 반환한다. 이 주소를 `kafka:9092` 하나로만 설정하면 compose 네트워크 밖에서 실행되는 `bootRun`과 테스트는 해당 호스트명을 해석할 수 없다. 따라서 내부용(`INTERNAL://kafka:9092`)과 외부용(`EXTERNAL://localhost:29092`) 리스너를 분리한다.

### 트림 기준: 그룹 전체의 미처리 최솟값

D-010에서는 "릴레이가 마지막으로 Kafka에 발행한 엔트리 ID"를 기준으로 잘랐으나, 이 방식은 릴레이 인스턴스가 여러 개일 때 **안전하지 않다.** 컨슈머 그룹이 엔트리를 나눠 주므로 한 인스턴스의 진행 지점 앞에 다른 인스턴스가 아직 처리 중인 엔트리가 있을 수 있다.

기준은 `XPENDING`이 돌려주는 **그룹 전체에서 가장 오래된 미처리 ID**다. 그 앞은 모든 인스턴스가 끝낸 구간이므로 자를 수 있다. 미처리가 하나도 없으면 그룹이 마지막으로 받아간 지점까지 자른다.

### 릴레이 처리 순서: Kafka 발행 먼저, XACK 나중, 미확인 메시지 먼저

한 스트림을 처리하는 순서다(`AuditRelayWorker`).

1. **현재 릴레이의 미확인 메시지를 재처리한다.** `XREADGROUP ... 0`으로 이 컨슈머가 **읽었지만 아직 XACK하지 못한 항목**을 다시 읽는다. 같은 `consumerName`의 릴레이가 계속 실행되거나 같은 이름으로 재시작하면 한 주기 안에 다시 처리한다.
2. **다른 릴레이의 오래된 PEL을 인계한다.** 복구 배치 한도가 남으면 `XAUTOCLAIM`으로 `min-idle-time`을 넘긴 항목을 현재 컨슈머로 옮긴다.
3. **새 기록을 처리한다.** `XREADGROUP ... >`이 빈 결과를 반환할 때까지 반복한다.
4. 각 배치: **모두 Kafka에 발행 → 성공을 확인한 항목만 XACK.** 실패한 항목은 미확인 상태로 남겨 다음 주기에 재시도한다.

**Kafka 발행 성공을 확인하기 전에 XACK하면 안 된다.** XACK 직후부터 Kafka 발행 전까지의 구간에 프로세스가 종료되면 Redis의 미확인 목록과 Kafka 양쪽에 기록이 남지 않아 데이터가 유실된다. Kafka 발행은 성공했지만 XACK 전에 프로세스가 종료되면, 같은 `consumerName`으로 재시작한 릴레이가 즉시 재발행하거나 다른 이름의 교체 릴레이가 `min-idle-time` 이후 메시지를 인계해 재발행한다. 컨슈머는 중복을 멱등하게 처리한다. 다만 이 종료 시점에 프로세스를 강제로 종료하는 장애 주입은 아직 수행하지 않았다.

### 현재 운용 경계와 Phase 3 정책

**Phase 2 완료 당시에는 단일 릴레이 + 고정 컨슈머 이름으로 제한했다.** `docker-compose.yml`의 `hostname: realtime-api`를 유지하고, 재시작한 릴레이가 `XREADGROUP ... 0`으로 자신의 PEL을 재처리했다. Phase 3 구현은 다른 이름의 교체 릴레이가 오래된 PEL을 인계하는 코드 경로를 추가했고, 이후 리더 선출로 여러 인스턴스 실행을 지원한다. 단, **활성 릴레이는 항상 하나다.**

#### Phase 3 범위

Phase 3는 **다른 이름의 릴레이로 교체되는 상황**과 **여러 인스턴스가 동시에 떠 있는 구성**을 지원한다. 모든 인스턴스가 릴레이 틱을 돌지만 PostgreSQL advisory lock을 쥔 인스턴스만 옮기고, 나머지는 틱을 건너뛴다. 여러 릴레이가 동시에 옮기는 구성은 여전히 범위 밖이다. 리더보드별 순서가 깨지기 때문이다.

- 컨슈머 이름은 인스턴스가 실행되는 동안 유지하고, 인스턴스마다 다르게 부여한다.
- 리더가 죽으면 세션이 끊겨 락이 풀리고, 다른 인스턴스가 다음 틱에 락을 잡아 새 메시지를 옮긴다.
- 이전 릴레이가 남긴 PEL은 새 릴레이가 `XAUTOCLAIM`으로 인계한다.
- 전달 방식은 최소 한 번 전달이다. 중복 발행은 허용하고 `(leaderboard_id, event_id)` 고유 제약으로 중복 저장을 막는다.
- 새 릴레이도 XACK 전에 종료되면 다음 릴레이가 같은 방식으로 다시 인계한다.

#### 릴레이 인계 정책

| 항목            | 결정                        | 근거                                                                                                                                                                |
| --------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `min-idle-time` | 10분                        | Kafka 프로듀서 기본 `delivery.timeout.ms` 120초보다 길게 두어 정상 처리 중인 메시지를 인계할 가능성을 낮춘다. 임시값이며 릴레이 배치 처리시간을 측정한 뒤 조정한다. |
| 복구 우선순위   | 복구 배치 후 새 메시지 처리 | 오래된 미처리 메시지를 먼저 처리하되 새 메시지 지연을 제한한다.                                                                                                     |
| 복구 배치 한도  | 스트림별 주기당 총 500건    | 현재 릴레이 배치 크기를 사용한다. 현재 컨슈머의 PEL 재처리와 다른 컨슈머의 PEL 인계를 합쳐 500건을 넘기지 않는다.                                                   |
| 남은 PEL        | 다음 주기에 이어서 처리     | `XAUTOCLAIM`이 반환한 커서부터 다음 복구 배치를 조회한다. 커서가 `0-0`이면 처음부터 다시 조회한다.                                                                  |
| 발행·확인 순서  | Kafka 발행 성공 후 XACK     | XACK 후 Kafka 발행 전에 종료되어 발생하는 유실을 막는다.                                                                                                            |

한 스트림의 처리 순서는 다음과 같다.

1. 현재 컨슈머의 PEL을 먼저 조회한다.
2. 복구 배치 한도가 남으면 다른 컨슈머의 PEL을 `XAUTOCLAIM`으로 인계한다.
3. 복구 배치를 Kafka에 발행하고 성공한 메시지만 XACK한다.
4. 새 메시지를 처리한다.
5. 남은 PEL은 다음 릴레이 주기에 이어서 처리한다.

다른 컨슈머의 PEL을 인계할 때만 `min-idle-time`을 적용한다. 새 릴레이가 인계한 뒤 발행에 실패한 메시지는 새 릴레이의 PEL에 남기고 다음 주기에 다시 처리한다.

#### 릴레이 자동 인계 구현과 장애 검증 (2026-08-19~2026-09-10)

`AuditRelayWorker`에 현재 컨슈머의 PEL 재처리 → `XAUTOCLAIM`으로 다른 컨슈머의 오래된 PEL 인계 → 새 메시지 처리 순서를 구현했다. `XAUTOCLAIM`의 반환 커서는 리더보드별로 보관하며, Kafka 발행에 성공한 엔트리만 XACK하는 기존 규칙을 그대로 사용한다.

Testcontainers 통합 테스트는 다음 경계를 검증한다.

- `stalePendingMessage_isClaimedByReplacementRelay_andStoredOnce`: 임시 컨슈머가 XACK하지 않은 PEL을 교체 릴레이가 인계해 PostgreSQL에 1행 저장하고 PEL을 0으로 만든다.
- `pendingMessage_isClaimedOnlyAfterMinIdle`: 메시지의 유휴 시간이 1초에 도달하기 전에는 PEL을 인계하지 않고, 1초가 지난 뒤에만 인계한다.
- `stalePendingMessages_areClaimedAcrossRecoveryBatches`: PEL 3건과 복구 배치 크기 2건을 사용해 다음 주기에 반환 커서부터 처리를 이어 간다.
- `stalePendingMessages_over500_areClaimedAcrossRecoveryCycles`: PEL 1,001건을 복구 한도 500건으로 세 주기에 걸쳐 `501 → 1 → 0`까지 해소한다. 로컬 Testcontainers 3회 측정에서 첫 500건 발행·XACK은 41~59ms였다.
- `replacementRelay_isClaimedAgainAfterItStopsBeforeAck`: A가 읽은 항목을 B가 인계한 뒤 B도 XACK하지 않은 상태에서 C가 다시 인계해 PostgreSQL에 1행만 저장한다.
- `kafkaPublishedBeforeCrash_isDeduplicatedWhenPendingMessageIsRelayedAgain`: Kafka 발행 후 XACK 전 상태를 만들고 같은 이벤트가 재발행돼도 PostgreSQL에는 1행만 남으며 PEL이 해소되는지 확인한다.

500건을 초과하는 PEL과 A → B → C 연속 인계는 Testcontainers로 검증했다. 2026-09-10에는 `scripts/verify-relay-handoff-10m.sh`로 Kafka를 중단해 Relay A가 PEL을 소유하게 한 뒤 A를 실제 `SIGKILL`하고, Kafka 복구 후 Relay B를 기동했다. 590,883ms까지 소유자가 A로 유지됐고 운영값 600,000ms 이후 B가 인계해 PEL 0건, PostgreSQL 1행으로 종료됐다. 여러 인스턴스 중 활성 릴레이를 하나로 제한하는 방식은 아래 리더 선출에서 다룬다.

500건 발행·XACK의 로컬 측정값 41~59ms는 초당 약 8,500건 이상으로 현재 목표 1,000/s보다 높다. 따라서 새 메시지의 주기당 처리 상한은 추가하지 않고 스트림이 빌 때까지 드레인하는 현재 방식을 유지한다. 실제 Compose 반복 측정에서 처리량이 목표 이하로 내려가거나 다른 리더보드가 굶으면 상한을 재검토한다.

#### 릴레이 리더 선출 (2026-11-16)

모든 인스턴스가 `AuditRelayWorker` 틱을 돌고, 틱 시작에서 `AuditRelayLeaderLock.isLeader()`가 참인 인스턴스만 옮긴다. 기존 PEL 인계(`XAUTOCLAIM`, 10분)는 그대로 둔다.

| 항목      | 결정                                                         | 근거                                                                                                                                                                                                                         |
| --------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 락 범위   | 세션 락 `pg_try_advisory_lock`, **풀 밖의 전용 연결**에 보관 | 리더가 바뀌지 않고 유지된다. 트랜잭션 락은 틱마다 다시 경쟁해 리더가 바뀔 수 있고, 그동안 풀 연결과 열린 트랜잭션을 Kafka 발행 대기(최대 120초) 내내 잡는다. Hikari 연결에 세션 락을 잡으면 `close()`가 세션을 살려 둔 채 풀로 돌려줘 락이 남는다 |
| 해제      | 연결 종료                                                    | 프로세스가 죽으면 연결이 끊기고 PostgreSQL이 세션 락을 푼다. 정상 종료 시에는 `@PreDestroy`에서 연결을 닫는다                                                                                                                  |
| 생존 확인 | 매 틱 `isValid(1)`                                           | 세션이 살아 있으면 락도 살아 있다. 끊겼으면 새 연결에서 다시 시도한다. 세션 락은 재진입되므로 쥔 동안에는 다시 호출하지 않는다                                                                                                  |
| 키        | 두 int 키 `(1, 1)`                                           | 스냅샷 락은 bigint 키를 쓴다. PostgreSQL은 bigint 키와 두 int 키의 공간을 분리하므로(`pg_locks.objsubid` 1 vs 2) 어떤 리더보드 UUID와도 겹치지 않는다                                                                         |
| 트림      | 리더에서만 실행                                              | 워터마크를 `XPENDING`과 `XINFO GROUPS` 두 번에 나눠 읽는다. 그 사이 다른 인스턴스의 릴레이가 새 기록을 읽으면 아직 XACK되지 않은 구간까지 자를 수 있다. 리더에서만 돌리면 릴레이와 같은 스케줄러 스레드에서 순서대로 실행된다 |
| 관측      | `audit_relay_leader` 게이지(1/0)                             | 인스턴스별로 리더 여부를 본다. 리더가 아닌 틱은 debug 로그만 남긴다                                                                                                                                                          |

Testcontainers 검증(`KafkaAuditRoundTripTest`):

- `twoRelayInstances_onlyLockHolderRelays_andStoresOnce`: 같은 Redis·Kafka·PostgreSQL에서 컨슈머 이름이 다른 릴레이 2개를 돌린다. 락이 없는 B는 메시지를 읽지 않고(미수신 3건 유지), A만 옮겨 PostgreSQL에 3행, `eventId` 중복 0건으로 저장된다.
- `leaderConnectionDies_otherInstanceTakesOverRelay`: A의 세션을 `pg_terminate_backend`로 끊어 크래시를 재현한다. B가 다음 틱에 락을 잡아 새 메시지를 옮기고, 다시 연결한 A는 락을 얻지 못해 옮기지 않는다. 최종 4행, 중복 0건, PEL 0건이다.

한계:

- advisory lock은 fencing token이 아니다. 리더 세션이 틱 도중에 끊기면 이전 리더는 그 틱을 끝까지 실행하고, 새 리더는 다음 틱부터 옮긴다. 최대 한 틱 동안 두 릴레이가 겹쳐 리더보드별 순서가 바뀔 수 있다. 유실은 없고 중복은 고유 제약이 흡수한다.
- 프로세스가 아니라 호스트나 네트워크가 끊기면 PostgreSQL이 죽은 연결을 감지할 때까지 락이 풀리지 않는다. 감지 시간은 서버의 `tcp_keepalives_*` 설정을 따르며 지금은 기본값이다.
- 실제 Compose에서 2인스턴스 `SIGKILL` 인계는 측정하지 않았다.

| 실패                  | 처리                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 파싱·레코드 검증 실패 | 3초 간격으로 최초 시도 포함 총 3회 처리한다. 최종 실패한 레코드만 DLQ(Dead Letter Queue)로 보낸다. DLQ 발행 성공 후 원본 오프셋을 커밋한다. |
| PostgreSQL 일시 장애  | `DataAccessResourceFailureException`과 `TransientDataAccessException` 계열만 같은 배치로 무기한 재시도한다. 대기 중에도 poll을 계속해 컨슈머 그룹 할당을 유지한다. |
| PostgreSQL 영구 오류  | 그 밖의 `DataAccessException`은 재시도로 해결되지 않는 코드·스키마 문제로 보고 컨슈머를 중단한다. DLT 전송과 오프셋 커밋은 하지 않고 오류 로그·메트릭을 남긴다. |

PostgreSQL 재시도는 10초부터 시작해 기준 간격을 2배씩 늘리고, 최대 5분으로 제한한다. 다중 컨슈머가 같은 DB 장애를 만나면 결정적 backoff는 재시도 시점을 계속 겹치게 한다. 별도 의존성 없이 각 기준 간격의 50~100% 범위에서 equal jitter를 적용했으며 최대 대기는 5분을 넘지 않는다.

2026-09-18 통합 테스트에서는 Kafka 파티션 0·2를 각각 맡은 컨슈머 2개에 PostgreSQL SQLSTATE `08006` 장애를 주입하고, 각 컨슈머의 실제 repository 호출 시각을 6회 기록했다. 400ms→800ms로 축소한 동일 시나리오에서 각 컨슈머의 첫 시도를 0으로 정규화한 누적 재시도 경과시간의 최대 편차는 결정적 backoff 4ms, equal jitter 115ms였다. 장애 해제 후 두 레코드가 저장되는 것까지 확인했다. 운영값 10초~5분의 실제 경과 시간은 측정하지 않았다.

```text
5~10초 → 10~20초 → 20~40초 → 40~80초 → 80~160초 → 150~300초 → 이후 150~300초
```

**DB 장애 중에는 릴레이도 멈춘다.** 릴레이는 매 틱 시작 시 PostgreSQL에서 리더보드 목록(`findAllIds()`)을 읽고 리더 락을 확인하므로, PostgreSQL에 연결할 수 없으면 해당 틱에서 아무것도 옮기지 않는다. 장애 동안 새 감사 기록은 Redis Stream에 쌓이고, 이미 Kafka에 있던 메시지는 Kafka 컨슈머 지연으로 남는다. DB가 복구되면 릴레이는 Stream 적체를 옮기고, 컨슈머는 미커밋 배치부터 재개한다. 적체가 `events.audit-stream.max-len`(100만 건)을 넘으면 옮기지 못한 오래된 기록부터 지워진다(피크 1,000/s 기준 약 16분). PostgreSQL pause/unpause 통합 테스트(`postgresOutage_keepsAssignmentAndOffset_thenStoresSameBatchAfterRecovery`)는 Kafka에 직접 발행한 메시지로 컨슈머만 검증했고 릴레이는 실행하지 않았다.

무기한 재시도는 자동 복구를 100% 보장한다는 뜻이 아니다. 방화벽·DNS·자격 증명 오류가 연결 예외로 나타나면 운영자 조치 전까지 계속 실패할 수 있다. 이 정책의 목적은 재시도가 안전한 동안 오프셋을 보존하고, DB가 복구됐을 때 별도 데이터 이동 없이 자동 재개하는 것이다. `(leaderboard_id, event_id)` 고유 제약과 `ON CONFLICT DO NOTHING`이 같은 배치의 중복 저장을 흡수한다.

재시도 시작부터 10분이 지나면 `auditConsumer` readiness를 `DOWN`으로 내리고 오류 로그를 한 번 남긴다. 재시도 횟수·지속 시간과 영구 오류는 Prometheus 메트릭으로 노출한다. 영구 오류로 중단된 컨슈머는 코드나 스키마를 수정한 뒤 다시 시작해야 하며, 미커밋 배치부터 처리한다.

#### Phase 3 검증 기준

- 릴레이 A가 Kafka 발행 전에 종료되면 릴레이 B가 10분 이후 PEL을 인계한다.
- 릴레이 A가 Kafka 발행 후 XACK 전에 종료되면 중복 발행이 발생해도 PostgreSQL에는 1행만 남는다.
- 릴레이 B도 XACK 전에 종료되면 다음 릴레이가 다시 인계한다.
- PEL이 500건을 넘으면 다음 릴레이 주기에서 이전 커서부터 처리한다.
- 릴레이 인스턴스 2개 중 advisory lock을 쥔 하나만 옮기고, PostgreSQL에는 이벤트당 1행만 남는다.
- 리더의 세션이 끊기면 다른 인스턴스가 다음 틱에 락을 잡아 새 메시지를 옮긴다.
- 파싱 실패 레코드는 3초 간격으로 총 3회 실패한 뒤 해당 레코드만 DLQ에 저장한다.
- DLQ 발행에 실패하면 원본 오프셋을 커밋하지 않는다.
- PostgreSQL 장애 중 컨슈머 그룹 할당을 유지하고 Kafka 컨슈머 지연이 증가한다.
- PostgreSQL 복구 후 같은 배치부터 재처리하고 컨슈머 지연이 0으로 돌아온다.
- SQL 문법·스키마 불일치 같은 영구 DB 오류는 컨슈머를 중단하고 원본 오프셋을 커밋하지 않는다.
- DB 재시도가 10분을 넘으면 readiness가 `DOWN`이고, 성공 후 `UP`으로 복귀한다.
- 독립 backoff execution 100개의 결정적 첫 간격은 모두 10초이고, equal jitter 적용 후에는 5~10초 범위에서 분산된다.
- Kafka 컨슈머 2개가 같은 PostgreSQL 장애에서 각각 실제 DB 저장을 6회 시도하며, 축소 backoff에서 첫 시도 기준 누적 재시도 경과시간의 최대 편차가 4ms에서 115ms로 증가한다.

#### 남은 리스크

- Testcontainers에서 500건 발행·XACK을 3회 측정한 값은 41~59ms다. 실제 Compose 환경의 500건 반복 측정은 하지 않았다.
- 새 메시지 유입량이 릴레이 처리량을 계속 넘으면 다음 복구 주기가 지연될 수 있다.
- 다중 컨슈머의 재시도는 equal jitter로 분산하지만, 모든 인스턴스가 최대 5분 안에 재시도하므로 DB 복구 직후의 일시적 부하는 남을 수 있다.
- 연결 오류 분류가 영구 원인을 완전히 배제하지는 못한다. 10분 readiness 실패와 재시도 지속 시간 메트릭을 운영 개입 조건으로 사용한다.

위 기준을 모두 검증했으며 Phase 3의 남은 범위는 없다.

### Kafka 컨슈머 재시작·다중 인스턴스 검증 (2026-08-11)

검증 목적은 릴레이를 단일 인스턴스로 유지한 채 Kafka 컨슈머만 늘릴 수 있는지 확인하는 것이다.

구성:

- app-1: 릴레이 활성화, Kafka 컨슈머 활성화
- app-2: 릴레이·스냅샷 워커·콜드 스타트 복구 비활성화, Kafka 컨슈머 활성화
- 두 컨슈머 모두 `audit-trend` 그룹 사용
- 토픽 파티션 3개, `leaderboardId`를 키로 사용

결과:

| 단계            | 파티션 할당                                               | 메시지 처리                                                                                      |
| --------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| app-1만 실행    | app-1 = `0, 1, 2`                                         | 모든 파티션의 컨슈머 지연 0                                                                      |
| app-2 추가      | app-1 = `0, 1`, app-2 = `2`                               | app-2가 파티션 2의 오프셋 `3173`을 처리해 다음 오프셋이 `3174`로 증가했고, PostgreSQL에 1행 저장 |
| app-2 강제 종료 | 기본 `session.timeout.ms=45000` 경과 후 app-1 = `0, 1, 2` | app-1이 파티션 2의 다음 오프셋 `3174 → 3175`를 처리하고 모든 파티션의 컨슈머 지연이 0으로 복귀   |

전체 `audit_events` 행 수는 검증 전 1,889행에서 신규 이벤트 9건 처리 후 1,898행으로 증가했다. 강제 종료 전후 파티션 2에 넣은 두 이벤트는 서로 다른 `eventId`로 각각 1행 저장됐다.

별도 Testcontainers 테스트에서는 리스너를 중지한 동안 같은 파티션에 메시지를 넣고 재시작했다. 첫 메시지의 커밋된 오프셋 이후부터 소비를 재개하고 두 메시지가 각각 1행인지 확인했다. 이 테스트는 리스너 재시작을 다루며 JVM 강제 종료를 재현하지는 않는다.

검증하지 않은 범위:

- DB 저장 성공 후 오프셋 커밋 직전 프로세스 종료
- 강제 종료 과정에서 실제 중복 전달 발생 여부. 중복 저장 방지는 동일 메시지를 두 번 전달하는 별도 테스트로 검증했다.
- API 요청의 인스턴스별 분산
- 단일 릴레이의 1,000 TPS 처리량과 API 응답 시간에 미치는 영향
- 중단된 릴레이가 남긴 미처리 메시지를 다른 릴레이가 인계받는 기능

> **Redis 자체 장애 시 복구 범위**: 스트림 본문과 컨슈머 그룹의 미확인 메시지 정보는 일반 Redis 데이터이고, `XREADGROUP`과 `XACK`은 쓰기 명령이므로 AOF에 기록된다. 따라서 재부팅 시 둘이 함께 복구된다(`appendfsync everysec` 기준 최대 1초 유실). Redis Streams 아웃박스는 릴레이 프로세스 중단에 대응하고, AOF/RDB는 Redis 장애에 대응한다. 1초 유실 구간에서 감사 기록이 사라지면 같은 Lua 블록의 점수도 함께 사라지므로 두 데이터가 어긋나지는 않는다(PRD 9 계층별 RPO).

### 릴레이 상태 확인: 미수신 건수와 미확인 건수

릴레이가 멈추면 Kafka로 아무것도 들어오지 않으므로 **Kafka 컨슈머 지연(lag)은 증가하지 않는다.** Kafka 지표만 보면 릴레이 장애를 확인하기 어렵다.

Redis Stream에서 아직 읽지 않은 항목은 `XINFO GROUPS`의 `lag`, 읽었지만 XACK하지 않은 항목은 `XPENDING`으로 확인한다. 릴레이가 읽기 전에 멈추면 XPENDING 건수는 늘지 않으므로 두 값을 함께 봐야 한다.

현재 `/internal/streams/status`는 릴레이 미수신 건수(`consumerGroupLag`), 미확인 건수(`pendingEntries`), 전체 길이(`streamLength`)를 제공한다. Prometheus에는 `stream_consumer_group_lag`와 `stream_pending_entries`가 등록되어 있다. Kafka 컨슈머 지연은 `/internal/kafka/audit-topic/status`와 Ops Console에서 커밋 오프셋 기준으로 확인한다. Prometheus에도 Spring Boot가 자동 등록하는 Kafka 클라이언트 메트릭 `kafka_consumer_fetch_manager_records_lag`가 있지만, fetch할 때만 갱신되므로 DB 재시도 중이거나 컨슈머가 멈추면 실제 지연을 반영하지 못한다. `streamLength`에는 이미 처리했지만 아직 트림하지 않은 항목도 포함되므로 적체량으로 사용하지 않는다.

### Redis 메모리 예산 (2026-11-16)

Redis는 `noeviction`이라 `maxmemory`에 닿으면 Lua의 SET·XADD가 OOM으로 거부되고 쓰기 API가 실패한다. 필요 메모리는 아래 식으로 잡는다. 285B·69B는 `artifacts/README.md` 실측값이다.

```text
Redis 필요 메모리 ≈ 멱등 TTL(86,400s) × 평균 TPS × 285B + 스트림 적체 × 69B
```

- 멱등 TTL 24시간은 클라이언트 재시도 계약이라 줄이지 않는다.
- 평균 1,000 TPS가 하루 내내 이어지면 멱등 키만 약 24.6GB다. 적체가 `max-len` 100만 건까지 차면 스트림당 약 69MB가 더해진다.
- 벤치마크의 256MB는 5분 측정용 조건이다. 1,000 TPS면 약 16분 만에 가득 차므로 운영 용량 기준으로 쓰지 않는다.
- 사용률은 `redis_used_memory_bytes / redis_maxmemory_bytes`로 본다. 80%를 5분 넘기면 `RedisMemoryHigh`가 뜨고, `maxmemory`가 0(무제한)이면 제외한다.

### 감사 기록 스키마

**필드**

| 필드             | 출처             | 비고                                           |
| ---------------- | ---------------- | ---------------------------------------------- |
| `type`           | Lua 분기         | `new` / `conflict`                             |
| `userId`         | ARGV             |                                                |
| `delta`          | ARGV             | `conflict`일 때는 **거부된(들어온) 값**        |
| `apiKeyId`       | ARGV (신규 추가) | 이상 탐지에서 클라이언트 단위 축               |
| `idempotencyKey` | ARGV (신규 추가) | `conflict` 기록을 원본 요청과 잇는 유일한 수단 |

`leaderboardId`는 값에 넣지 않는다. Kafka 메시지 키로 쓰이며 레코드에 함께 저장되므로 컨슈머가 `record.key()`로 읽는다. 레코드를 다른 토픽이나 시스템으로 복사해야 할 때 값에도 추가한다. 필드를 나중에 추가해도 기존 컨슈머의 파싱은 깨지지 않는다.

**이벤트 발생 시각**은 별도 필드를 두지 않는다. 스트림 엔트리 ID의 앞부분이 XADD 시점의 밀리초이며, 컨슈머가 이 값을 PostgreSQL의 `event_time`으로 저장한다. 현재 릴레이는 `ProducerRecord`에 타임스탬프를 지정하지 않으므로 Kafka 레코드에는 발행 시각이 들어간다. 따라서 릴레이가 밀린 뒤 오래된 엔트리를 발행해도 적재 직후 `retention.ms` 삭제 대상이 되지는 않는다.

**형식**은 JSON. 스트림의 평평한 필드-값 구조는 Redis의 저장 방식이지 전송 형식이 아니다. 릴레이가 변환 지점이므로 컨슈머가 다루기 쉬운 형식으로 내보낸다. 필드명 반복으로 인한 크기 증가는 `compression.type`으로 흡수한다.

**버전**은 Kafka 헤더에 둔다. 값을 파싱하지 않고도 버전을 알 수 있어 컨슈머가 분기하기 쉽다.

**토픽 정리 정책은 `delete`를 유지한다.** `compact`는 키마다 마지막 값만 남기므로, 리더보드가 키인 이 토픽에 걸면 리더보드당 이벤트 한 건만 남고 나머지가 사라진다. 감사 로그에는 쓸 수 없다.

## 실무 스펙 기준선

데모 수준과 실제 운영 수준을 가르는 최소 조건이다. 지키지 못하는 항목은 **지키지 못했다는 사실과 이유를 문서에 남긴다.**

- **오프셋은 처리 완료 후 커밋한다.** auto-commit을 끄고 `ack-mode=batch`를 사용해 리스너가 정상 반환한 뒤 컨테이너가 배치 오프셋을 커밋한다 (항목 6·11의 전제).
- **컨슈머는 멱등하게 구현한다.** 최소 한 번 전달 방식에서는 중복 처리가 예외가 아니라 정상 경로다. PostgreSQL의 `(leaderboard_id, event_id)` 고유 제약과 `ON CONFLICT DO NOTHING`으로 중복 저장을 막는다.
- **리텐션은 기간과 용량을 병기한다.** 어느 쪽이 먼저 걸리는지를 알고 설정한다.
- **복제 계수는 낮게 설정하되 근거를 남긴다.** 로컬 Docker Compose에서 브로커 3대를 실행하면 검증 범위보다 인프라 복잡도가 커진다. `replication.factor=1`로 두되 "프로덕션에서는 `acks=all` + `replication.factor≥3` + `min.insync.replicas=2`"를 문서에 명시한다. **운영 요구사항을 인지하고 의도적으로 제외한 결정과 요구사항을 검토하지 않은 상태를 구분해야 한다.**
- **처리 지연은 기존 운영 화면에서 확인한다.** 별도 모니터링 스택을 세우지 않고 내부 API, Prometheus, Ops Console을 사용한다.

## 컨슈머와 저장 (2026-08-07 착수)

첫 컨슈머인 `AuditEventConsumer`가 audit 토픽을 읽어 **원본 이벤트를 PostgreSQL `audit_events`에 적재**한다. 이 구현으로 ADR-009의 가정 2인 복수 소비자 지원을 실제 구조에 반영한다.

**원본 적재를 고른 이유**: 추이 집계 결과만 저장하면 데이터 크기는 작지만, 이상 탐지와 아카이브에는 원본이 필요하다. 원본을 저장하면 추이 집계, 이상 탐지와 아카이브가 같은 데이터를 재사용할 수 있다. 추이는 `date_bin`을 사용한 5분 버킷으로 집계하고, 이상 탐지와 아카이브는 원본을 사용한다. 현재 데모 규모에서는 집계 쿼리의 응답 시간이 문제가 되지 않는다. 데이터가 증가해 집계 쿼리가 병목이 되면 롤업 요약 테이블을 추가한다.

**멱등은 DB가 맡는다**: 릴레이의 재전송이나 Kafka 컨슈머의 재처리로 같은 이벤트가 두 번 올 수 있다. `UNIQUE (leaderboard_id, event_id)` + `ON CONFLICT DO NOTHING`으로 중복을 집계 전에 제외한다. 집계가 두 번 반영되면 유저가 이상 탐지 등에서 불이익을 받는다. **엔트리 ID는 한 리더보드 스트림 안에서만 고유**하므로 `leaderboard_id`와 함께 유일성 조건을 구성한다. 릴레이는 메시지에 엔트리 ID(`eventId`)를 포함한다. V7 파티셔닝 이후 실제 제약은 `UNIQUE (leaderboard_id, event_id, event_time)`이다. 파티션 테이블의 UNIQUE는 파티션 키를 포함해야 하기 때문이다. `event_time`은 `event_id`의 ms 부분에서만 계산하므로 같은 이벤트는 항상 같은 `event_time`, 같은 파티션에 들어가고 중복 판정은 그대로다.

**오프셋은 처리 후 커밋**: 배치 리스너 + `auto-commit=false`. 컨테이너가 배치를 적재한 뒤에만 오프셋을 커밋한다(릴레이의 XACK와 같은 규칙). 배치 크기는 `max-poll-records`(개수)와 poll 주기(시간) 중 먼저 걸리는 쪽이다.

### 저장 티어링: hot(PG) / cold(객체 스토리지)

30일치 원본을 PostgreSQL에 유지하면 모든 집계 쿼리의 스캔 범위가 커지고, 자주 조회하지 않는 데이터까지 상대적으로 비싼 저장소에 남는다. 약 3GB의 저장 용량 자체보다 집계 쿼리의 성능 부담이 주요 문제다.

- **hot**: 최근 원본과 추이 집계는 **PostgreSQL**에 저장한다. 이 데이터는 자주 조회하며 크기가 상대적으로 작다.
- **cold**: **30일이 지난 원본은 객체 스토리지로 아카이브한다.** 하루 단위 파일(`20260812`, `20260813`, …)로 기록하고, 필요한 구간만 다운로드해 이상 조사와 감사에 사용한다.

객체 스토리지는 저장 비용보다 다운로드 비용이 상대적으로 크므로, 자주 조회하지 않는 원본을 보관할 때 적합하다. 자주 조회하는 추이 집계는 PostgreSQL에 유지한다.

로컬 데모에 객체 스토리지를 붙이는 것은 비목표다. 티어링 설계를 문서로 남기는 것이 목적.

#### hot 보관 구현: 일 단위 파티션 + DROP (2026-11-16)

아카이브는 비목표로 두고 hot 30일만 구현했다. 30일이 지난 원본은 아카이브 없이 지운다.

- `V7__partition_audit_events_by_day.sql`: `audit_events`를 `event_time` 기준 UTC 일 단위 범위 파티션 테이블로 바꿨다. PG는 기존 테이블을 파티션 테이블로 ALTER할 수 없어서 새 테이블 생성 → 기존 행이 걸친 날짜의 파티션 생성 → 행 복사 → 기존 테이블 DROP → 이름 변경을 한 트랜잭션으로 한다. PK는 `(id, event_time)`, UNIQUE는 `(leaderboard_id, event_id, event_time)`이다.
- `AuditEventPartitionJob`: 기동 시 한 번, 이후 매시 정각(UTC)에 오늘과 그 뒤 3일의 파티션을 `CREATE TABLE IF NOT EXISTS ... PARTITION OF`로 만들고, 날짜가 `오늘 - 30일`보다 이른 파티션을 `DROP TABLE IF EXISTS`로 지운다. 설정은 `events.consumer.partition-retention-days=30`, `events.consumer.partition-ahead-days=3` 두 개뿐이다. 3일을 미리 만들어 두면 잡이 주말 내내 실패해도 적재가 멈추지 않는다.
- 다중 인스턴스: 한 트랜잭션 안에서 `pg_advisory_xact_lock`을 잡고 실행한다. 늦게 온 인스턴스는 기다렸다가 할 일이 없는 상태로 끝난다. 락이 없으면 `IF NOT EXISTS` 확인과 생성 사이에 다른 세션이 끼어들어 카탈로그 중복 키 오류가 날 수 있다.
- DELETE 대신 DROP: 파티션 하나를 통째로 지우므로 dead tuple·VACUUM 부담이 없다. 추이 조회는 `event_time` 조건으로 해당 날짜 파티션만 스캔한다. prepared statement의 generic plan에서도 실행 시점 pruning(`Subplans Removed`)이 동작한다.
- DEFAULT 파티션은 두지 않는다. DEFAULT 파티션에 어떤 날짜의 행이 들어가 있으면 그 날짜의 파티션을 나중에 만들 때 실패하고, 잘못 들어온 행이 보관 정책 밖에 계속 남는다.

알려진 경계(필터링 로직은 추가하지 않았다):

1. 파티션이 없는 날짜의 INSERT는 SQLSTATE `23514`(`no partition of relation found for row`)로 실패한다. Spring은 이를 `DataIntegrityViolationException`으로 바꾸고, 컨슈머 에러 핸들러는 일시 장애(`DataAccessResourceFailureException`, `TransientDataAccessException`)가 아니므로 **영구 오류로 분류해 컨슈머를 중단한다.** 오프셋은 커밋하지 않으므로 유실은 없고, 해당 날짜의 파티션을 만든 뒤 컨슈머를 재시작하면 같은 배치부터 다시 처리한다. 파티션 잡이 3일 넘게 실패하거나 Redis 서버 시계가 3일 넘게 앞서면 이 경로를 탄다.
2. Kafka 보관 기간도 30일이고, 세그먼트 단위로 지우므로 30일을 조금 넘긴 레코드가 남아 있을 수 있다. 오프셋을 `earliest`로 되감으면 PG에서 이미 DROP한 날짜의 이벤트가 다시 올 수 있고, 1번과 같이 컨슈머가 중단된다. 되감기는 30일 경계 안쪽 시점으로 지정해야 한다.

### 이상 탐지: 필드 확장 선행

현재 엔트리의 `userId`와 `delta`만으로는 평균 대비 이상 점수를 탐지하거나 payload 변형 요청을 분류하기 어렵다. 출처와 디바이스 같은 필드를 먼저 추가해야 할 가능성이 높다(항목 10 스키마 정책). 원본은 이미 `audit_events`에 저장되므로 조회 기반은 확보돼 있다.

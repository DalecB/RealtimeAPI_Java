# SPIKE-001: Kafka 도입 설계 검증

**상태:** 계획 (2026-07-27 작성, 2026-07-28 갱신)
**관련 결정:** [PRD ADR-009](PRD.md) — Audit Log 소비 도입 여부와 전송 계층 선택

---

## 이 문서가 있는 이유

ADR-009가 Kafka 채택을 확정했다. 이 문서는 **그 결정을 실무에서 쓰이는 스펙으로 구현하기 위해 무엇에 답해야 하는지**를 고정한다.

Kafka는 "붙이면 도는" 종류가 아니다. 브로커를 띄우고 토픽 하나에 컨슈머 하나를 붙이면 동작은 하지만, 그 상태는 운영 스펙이 아니다. 아래 검증 항목은 **동작 확인이 아니라 결정과 근거**를 산출물로 한다. 구성이 뜨는 것은 검증의 시작점이지 결과가 아니다.

---

## 선결 쟁점: ADR-002와의 충돌 〔B 채택 — 2026-07-29〕

ADR-002는 XADD를 Lua 블록 안에 넣어 "score는 반영됐는데 Audit Log에 누락"되는 상황을 원천 차단했다. **Kafka producer는 Lua 블록 안에 들어갈 수 없다.** 따라서 원자성 보장을 어디로 옮길지가 Kafka 도입의 선결 조건이다.

### 검토한 안

| 안 | 구조 |
| --- | --- |
| **A. Redis 성공 후 produce** | 핫패스에서 Lua 성공 → 그 자리에서 Kafka produce |
| **B. Streams를 outbox로** | Lua의 XADD 유지 → 별도 relay가 stream을 읽어 Kafka로 전달 |
| **C. XADD를 Kafka로 대체** | Lua에서 XADD 제거, 기록은 Kafka에만 |

### 판별 기준

갈림길은 하나다 — **원자 블록 안에 내구적 기록이 남는가.**

서로 다른 두 시스템에 걸친 쓰기에는 원자적 커밋이 없다. 분산 트랜잭션은 비용과 가용성 때문에 선택지가 아니다. 그러므로 남는 방법은 **한 시스템 안에서 원자적으로 쓰고, 그 기록을 비동기로 옮기는 것**뿐이다. 기록이 내구적이면 옮기는 쪽은 안전하게 재시도할 수 있다.

### 결정: B

Lua의 4연산 원자성을 유지하되, 스트림의 역할을 **최종 저장소에서 outbox로** 바꾼다. relay가 스트림을 읽어 Kafka로 옮기고, Kafka가 최종 저장소이자 소비 계층이 된다. ADR-002는 뒤집히지 않고 유지된다.

### 탈락 사유

**C — 유실을 감지할 수도 복원할 수도 없다.** Lua가 끝난 뒤 produce 전에 프로세스가 죽으면 그 기록은 영구 유실된다. 복구 시 대조하려 해도 비교 대상이 없다.

- ZSET은 **집계**다. score가 500일 때 100×5인지 100×4에 1건 누락인지 구분할 수단이 없다. 로그 한 건이 빠져도 집계에는 흔적이 남지 않는다.
- 멱등키는 `v2:<payloadHash>:<processedAt>` 형식으로 **해시**를 담는다. "이 키로 무언가 처리됐다"는 알 수 있어도 userId·delta를 복원할 수 없다. TTL 24시간이 지나면 그 흔적조차 없다.

즉 C의 비용은 "복구가 비싸다"가 아니라 **"유실을 알 방법이 없다"** 이다.

**A — 독립된 안이 아니다.** A는 produce 실패를 어떻게 다루느냐에 따라 둘로 무너진다.

- 실패를 처리한다면 스트림에서 재전송해야 하고, 그것이 곧 **B**다.
- 처리하지 않는다면 기록이 유실되고, 그것이 곧 **C**다.

중간 상태로 유지되지 않으므로 별도 안으로 세우지 않는다.

### B의 비용

relay 지점에서 **at-least-once 중복이 발생한다.** `XREADGROUP` → produce → `XACK` 순서에서 produce 성공 후 XACK 전에 죽으면 재전달되어 Kafka에 중복이 들어간다. 이는 구조상 피할 수 없으며, 컨슈머 멱등성으로 흡수한다(아래 실무 스펙 기준선).

## 확정된 구현 결정 (2026-07-29)

### relay 위치 — 애플리케이션 내부

`@Scheduled` 기반으로 앱 안에 둔다. ADR-003의 snapshot worker와 같은 형태이며, 배포 단위를 하나로 유지한다.

비용: 핫패스와 JVM 힙·커넥션을 공유한다. relay가 밀리면 그 영향이 API 응답에 나타날 수 있으므로, 처리량이 문제가 되면 별도 프로세스로 분리하는 것이 다음 단계다.

### 파티션 키 — `leaderboardId`

**근거**: 추이 집계는 리더보드 단위로 이루어진다. 이상 탐지도 대개 한 리더보드 안에서의 유저 행동을 보므로, 이 키로도 해당 유저의 이벤트가 한 파티션에 순서대로 모인다.

**비용**: PRD `0. Scenario`가 선언한 리더보드 단위 트래픽 편향이 그대로 파티션 편중이 된다. 한 키는 여러 파티션으로 나눌 수 없으므로 뜨거운 리더보드는 컨슈머를 늘려도 병렬 처리되지 않는다. 또한 리더보드 개수가 유효 병렬도의 상한이 된다.

**받아들이는 이유**: 시스템 전체 피크가 1,000/s이므로 파티션 하나가 전부 받아도 Kafka 처리 범위 안이다.

**상한에 닿았을 때의 경로**: 복합 키(`leaderboardId:bucket`)로 뜨거운 리더보드만 여러 파티션에 분산한다. 대가는 리더보드 단위 순서 보장을 잃는 것이다. 현 규모에서는 필요하지 않으므로 도입하지 않는다.

### 순서 보장 범위

리더보드 단위로 보장된다. 서로 다른 리더보드 사이에는 순서가 없다. 컨슈머는 이를 전제로 작성한다.

### replay — 기록하지 않음

멱등키가 존재하는 재요청은 정상적인 클라이언트 재시도이며 이상 탐지 신호로서 값이 낮다. 건수는 `idempotency_hit_total`로 이미 계측되고 있으므로 추세 파악은 가능하다.

현재 Lua는 멱등키가 존재하면 XADD 전에 early return 하므로 **이 동작은 기존 코드 그대로다**(`process_event.lua:10-16`, `ProcessEventConcurrencyTest`가 동시 50건에 `XLEN = 1`을 단언).

### 409 (멱등키 재사용 충돌) — Lua에서 기록

동일 키에 다른 payload가 오는 경우는 클라이언트의 키 생성 버그이거나 변조 시도이므로 이상 탐지에서 값이 높다. 따라서 감사 기록에 남긴다.

Lua가 저장된 값과 들어온 값의 해시 부분을 비교해 불일치일 때 XADD 한다. 원자성 때문이 아니다 — 409는 점수가 반영되지 않은 경로라 ADR-002가 막으려는 상황 자체가 없다. **스트림에 쓰는 곳을 한 군데로 유지하기 위해서다.** 생산자가 둘이 되면 필드 구성과 실패 처리를 두 군데서 맞춰야 한다.

PRD `7.2 Lua 제약 조건`의 반복문 금지를 지키기 위해, 구분자 위치는 `string.find`로 찾고 `string.sub`으로 자른다. 순회하지 않는다.

### outbox 트림 — relay가 보낸 지점까지만

`XTRIM key MINID <relay가 마지막으로 produce한 엔트리 ID>`

**고정 길이나 고정 기간으로 자르지 않는다.** `MAXLEN`은 읽혔는지를 보지 않으므로, relay가 밀린 상태에서 트림이 앞지르면 **아직 Kafka로 옮기지 못한 엔트리가 조용히 사라진다.** outbox가 유실 방지를 위해 존재하는데 그 outbox가 유실되는 상태다.

relay 진행 기준으로 자르면 이 경로가 구조적으로 막힌다. 보내지 않은 것은 정의상 삭제 대상이 아니고, 스트림 크기가 relay 지연만큼으로 자동 조절되어 튜닝할 시간 상수가 없다.

기존 `MAXLEN ~ 100000`은 그대로 둔다. relay가 영구히 멈췄을 때 무한 증식을 막는 최후 방어선이다.

### relay 구성값

| 값 | 설정 | 비고 |
| --- | --- | --- |
| relay 주기 | 5초 | 한 틱 안에서 **스트림이 빌 때까지 반복해서** 읽는다. 한 번에 가져오는 건수를 고정하면 유입이 그보다 많을 때 밀린 양이 줄지 않는다 (피크 1,000/s면 5초에 5,000건) |
| 트림 주기 | 40초 | 이미 옮긴 엔트리를 정리하는 주기. 유실 위험이 아니라 메모리를 줄이는 값이다 — `MAXLEN`은 오래된 것부터 지우므로 이미 옮긴 것이 먼저 지워진다 |
| 컨슈머 이름 | `HOSTNAME` | `docker-compose.yml`에서 `hostname`을 고정한다. 기본값인 컨테이너 ID를 쓰면 재생성 때마다 이름이 바뀌어 이전 이름의 미처리 항목이 주인 없이 남는다 |
| 스트림 순회 | 리더보드별 반복 | `XREADGROUP`에 여러 스트림을 한 번에 넘기면 왕복이 줄지만, Redis Cluster에서 키가 다른 슬롯이면 `CROSSSLOT`으로 실패한다. `{leaderboardId}` 해시 태그를 붙인 이유(ADR-002)가 Cluster 대비이므로 그 준비를 무효화하지 않는다. `SnapshotCaptureWorker`가 이미 같은 순회 형태다 |
| 그룹 생성 | 매 틱 시도, `BUSYGROUP` 무시 | 새 리더보드의 스트림에는 그룹이 없다. 여러 인스턴스가 동시에 만들어도 하나만 성공하므로 별도 잠금이 필요 없다 |

### 토픽 설정

토픽은 애플리케이션 기동 시 `NewTopic` 빈으로 만든다(`AuditTopicConfig`). 브로커의 auto-create를 껐으므로 이 빈이 없으면 토픽이 없다. 리텐션·정리 정책을 코드로 박아두는 것이 목적이다.

| 값 | 설정 | 비고 |
| --- | --- | --- |
| 이름 | `lb-audit-events` | 하이픈 표기. 점 표기는 계층이 있을 때 쓰는데 이 토픽은 하나뿐이고, Kafka 메트릭에서 `.`과 `_`가 서로 뭉개지는 문제가 있어 피한다 |
| 파티션 | 3 | **처리량이 아니라 한 컨슈머 그룹에서 병렬로 돌릴 인스턴스 수의 상한이다.** 피크 1,000/s는 파티션 하나로도 남으므로 처리량은 기준이 못 된다. 앱 인스턴스 3대까지 부하를 나눠 갖는다는 뜻. 1이면 다중 인스턴스 결정(D-013)과 모순되고, 크게 잡으면 리더보드가 적을 때 빈 파티션만 늘어난다 |
| `retention.ms` | 30일 | ADR-009 가정 1 |
| `retention.bytes` | 1GB | **로컬 기준값이다.** 30일치는 약 2GB로 추산되므로 실제 부하에서는 용량 제한이 시간보다 먼저 걸린다. 운영에서는 늘려야 한다 |
| `cleanup.policy` | `delete` | `compact`는 키마다 마지막 값만 남겨 감사 로그를 파괴한다 |

**파티션을 늘려야 할 때 순서가 깨지는 문제**: 파티션은 줄일 수 없고, 늘리면 `키→파티션` 매핑이 다시 계산되어 그 순간 옮겨간 키의 순서가 잠깐 섞인다. 우리 소비자 둘은 여기에 대한 민감도가 다르다. **추이 집계는 합산이라 순서와 무관해 재분할에도 무해**하고, **이상 탐지만 경계 시점에 짧은 교란**을 겪는다(그마저도 영구가 아니라 옮겨간 키가 새 파티션에서 다시 순서를 잡을 때까지다). 즉 "3으로 시작하고 필요하면 늘린다"가 무책임하지 않은 이유는, 소비자 하나는 영향이 없고 다른 하나만 관리 가능한 일시 교란이기 때문이다.

**호스트와 compose 양쪽에서 접속하려면 리스너가 둘이어야 한다**: 브로커는 클라이언트가 처음 붙은 뒤 "이 주소로 다시 연결하라"고 접속 주소를 돌려준다. 이 주소를 `kafka:9092` 하나로만 두면 compose 네트워크 밖(호스트의 `bootRun`·테스트)에서는 그 이름을 못 찾는다. 그래서 안쪽용(`INTERNAL://kafka:9092`)과 바깥쪽용(`EXTERNAL://localhost:29092`)을 나눠 둔다.

### 트림 기준 — 그룹 전체의 미처리 최솟값

D-010에서 "relay가 마지막으로 produce한 엔트리 ID"로 잘랐으나, **인스턴스가 여럿이면 이 기준은 안전하지 않다.** 컨슈머 그룹이 엔트리를 나눠 주므로 한 인스턴스의 진행 지점 앞에 다른 인스턴스가 아직 처리 중인 엔트리가 있을 수 있다.

기준은 `XPENDING`이 돌려주는 **그룹 전체에서 가장 오래된 미처리 ID**다. 그 앞은 모든 인스턴스가 끝낸 구간이므로 자를 수 있다. 미처리가 하나도 없으면 그룹이 마지막으로 받아간 지점까지 자른다.

### relay 건강 지표 — `stream_pending_entries`

relay가 멈추면 Kafka로 아무것도 들어오지 않으므로 **컨슈머 lag은 자라지 않는다.** Kafka 쪽 지표만 보면 조용한 장애가 된다.

relay가 컨슈머 그룹으로 스트림을 읽기 시작하면 `stream_pending_entries`가 그룹의 PEL 크기를 반영하게 된다. 지금까지 상수 `0`이던 이 값이 그 시점부터 **relay 건강 지표**가 된다. 값이 계속 자라면 relay가 밀리거나 멈춘 것이다.

### 감사 기록 스키마

**필드**

| 필드 | 출처 | 비고 |
| --- | --- | --- |
| `type` | Lua 분기 | `new` / `conflict` |
| `userId` | ARGV | |
| `delta` | ARGV | `conflict`일 때는 **거부된(들어온) 값** |
| `apiKeyId` | ARGV (신규 추가) | 이상 탐지에서 클라이언트 단위 축 |
| `idempotencyKey` | ARGV (신규 추가) | `conflict` 기록을 원본 요청과 잇는 유일한 수단 |

`leaderboardId`는 값에 넣지 않는다. Kafka 메시지 키로 쓰이며 레코드에 함께 저장되므로 컨슈머가 `record.key()`로 읽는다. 레코드가 다른 토픽이나 시스템으로 복사될 일이 생기면 그때 값에도 추가한다 — 나중에 필드를 늘려도 컨슈머는 깨지지 않는다.

**시각**은 별도 필드를 두지 않는다. 스트림 엔트리 ID의 앞부분이 XADD 시점의 밀리초이며, 앱 인스턴스가 여럿이어도 Redis 서버 시계 하나를 쓰므로 인스턴스 간 시계 차이가 없다. relay는 이 값을 Kafka 레코드 타임스탬프로 지정한다. 단 `retention.ms`가 이 타임스탬프를 기준으로 동작하므로, relay가 크게 밀린 상태에서 오래된 엔트리를 보내면 적재 직후 리텐션 대상이 될 수 있다.

**형식**은 JSON. 스트림의 평평한 필드-값 구조는 Redis의 저장 방식이지 전송 형식이 아니다. relay가 변환 지점이므로 컨슈머가 다루기 쉬운 형식으로 내보낸다. 필드명 반복으로 인한 크기 증가는 `compression.type`으로 흡수한다.

**버전**은 Kafka 헤더에 둔다. 값을 파싱하지 않고도 버전을 알 수 있어 컨슈머가 분기하기 쉽다.

**토픽 정리 정책은 `delete`를 유지한다.** `compact`는 키마다 마지막 값만 남기므로, 리더보드가 키인 이 토픽에 걸면 리더보드당 이벤트 한 건만 남고 나머지가 사라진다. 감사 로그에는 쓸 수 없다.

>
> 11은 ADR-009에 적어둔 관측 비교를 실제로 확인하는 항목이다. Redis Streams는 `XINFO GROUPS`의 lag과 `XPENDING`의 pending·idle을 합쳐 봐야 하고, Kafka는 컨슈머 그룹 lag 하나로 답한다 — **단 6에서 manual commit을 골랐을 때만 그렇다.** auto-commit이면 Kafka lag도 처리 여부를 반영하지 못한다.

## 실무 스펙 기준선

데모 수준과 실제 운영 수준을 가르는 최소 조건이다. 지키지 못하는 항목은 **지키지 못했다는 사실과 이유를 문서에 남긴다.**

- **오프셋은 처리 완료 후 수동 커밋.** auto-commit은 쓰지 않는다 (항목 6·11의 전제).
- **컨슈머는 멱등하게 구현한다.** at-least-once이므로 중복 처리는 예외가 아니라 정상 경로다. 판정 기준은 `12. Idempotency 정책`의 payload 해시 비교 방식을 재사용한다.
- **리텐션은 기간과 용량을 병기한다.** 어느 쪽이 먼저 걸리는지를 알고 설정한다.
- **복제 계수는 낮게 가되 근거를 남긴다.** 로컬 compose에서 브로커 3대는 과하다. `replication.factor=1`로 두되 "프로덕션에서는 `acks=all` + `replication.factor≥3` + `min.insync.replicas=2`"를 문서에 명시한다. **아는데 안 한 것과 모르는 것은 구분되어야 한다.**
- **lag은 기존 대시보드에 편입한다.** 별도 모니터링 스택을 세우지 않는다 — 이미 Prometheus와 Grafana가 있다.
